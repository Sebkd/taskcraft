# Design: `Queue::on_store` выводит тип аргументов без регистрации

> **Change**: [change.md](change.md)
>
> **Статус**: Отложено до 0.4 (решение 2026-10-13: несовместимые изменения — одним заходом)
>
> **Автор**: Андрей Серохвостов
>
> **Дата**: 2026-10-13

---

## Context

`task_fn` возвращает `TaskFn<F, Args, X>` (`crates/taskcraft/src/handler.rs:388`), и этот тип несёт аргументы задачи. Но `Queue::builder`, `Queue::consumer` и `Queue::on_store` (`crates/taskcraft/src/queue.rs:151`, `:165`, `:201`) не накладывают на `Svc` никаких границ. `Args` очереди связывается с сервисом только в `Monitor::register` (`monitor.rs:269`, `Svc: Service<TaskRequest<Args>>`). Без `register` в той же функции компилятор просит аннотацию (E0283). Так было и в примере README пакета Kafka (BL-39): там пришлось добавить скрытый `register`.

Проверено экспериментом (откатан):
- граница `where Svc: tower::Service<TaskRequest<Args>>` в трёх конструкторах — и `Queue::builder(…, task_fn(|n: u32| …)).build()` компилируется без аннотаций и без `register`;
- `cargo semver-checks` этого не замечает («no semver update required»);
- но собственный тест `crates/taskcraft/tests/worker.rs:51` (`fn queue_of<Svc>(…) { Queue::builder(…, service) }`) перестаёт собираться: обобщённая обёртка без такой границы — E0277.

Значит, для пользователей, которые оборачивают конструкторы своим обобщённым кодом, изменение **несовместимо**, хотя инструмент его не ловит.

## Goals / Non-Goals

**Goals**
- `Queue::builder`/`consumer`/`on_store` с `task_fn` выводят `Args` без аннотаций и без `register`.

**Non-Goals**
- Другие изменения сигнатур.

## Decisions

### D-1. Граница `Svc: tower::Service<TaskRequest<Args>>` в трёх конструкторах

Только эта граница: её достаточно для вывода, и она самая слабая из требований `register`. Остальные (`Response = Outcome`, `Clone`, `Send`) остаются в `register`, как сейчас.

### D-2. Выпуск — 0.4, а не 0.3.x (отступление от заявки)

Заявка допускала 0.3.x, «если `semver-checks` не возразит». Инструмент не возразил, но эксперимент показал реальную поломку обобщённого кода (Context, `worker.rs`). Обещание 0.x: в младшей части версии только совместимые изменения. Поэтому изменение идёт в 0.4 — вместе с BL-45 (`driver-errors-wrapped`), тоже несовместимым. До выпуска 0.4 изменение лежит в master: следующие выпуски 0.3.x из master не делаются, пока 0.4 не вышла. Если понадобится срочное исправление 0.3.x — ветка от тега `v0.3.2`.

В `MIGRATION.md` — раздел «0.3 → 0.4»: обобщённая обёртка над конструктором очереди добавляет `Svc: tower::Service<TaskRequest<Args>>`.

### D-3. Тесты

- Doc-тест в документации `Queue::on_store` и `Queue::builder`: очередь собирается без `register` и без аннотаций.
- `tests/worker.rs`: хелпер `queue_of` получает границу — это и есть пример миграции.
- Пример в README пакета Kafka: скрытый `register` убирается — он был обходом.

### D-4. Версия в манифестах

Подъём до 0.4.0 — в ветке выпуска 0.4, не здесь. CI `semver-checks` сейчас изменение не ловит, поэтому master остаётся зелёным.

### Спецификация

- 2.5: «Конструкторы очереди связывают тип аргументов с сервисом: очередь на `task_fn` строится без указания типа» (несовместимое уточнение, 0.4).
- Критерий из раздела 16 заявки — №96.
- Таблица статусов: «реализовано (выпуск 0.4)», версия спецификации.

## Risks / Trade-offs

- master копит несовместимые изменения до 0.4. Пока это одна заявка, а BL-45 тоже про 0.4.
