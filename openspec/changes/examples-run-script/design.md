## Context

Пятнадцать примеров (E-1…E-15, `examples/README.md`) CI собирает и проверяет линтером, но не запускает — так решено. Перед выпуском их запускают вручную, по одному, без записанного порядка.

Что упрощает автоматизацию:
- каждый пример проверяет свой результат сам и при расхождении выходит с ошибкой (`examples/README.md`) — скрипту достаточно кода выхода;
- E-12…E-14 читают адреса из `TASKCRAFT_KAFKA_BROKERS` и `TASKCRAFT_POSTGRES_URL`; `examples/docker-compose.yml` поднимает Kafka и PostgreSQL;
- `graceful-shutdown` (E-6) без Ctrl-C останавливается сам через 3 с.

Что требует сценария:
- `axum-service` (E-11) — отдельный пакет; HTTP-сервер работает до Ctrl-C на `127.0.0.1:3000`.

## Goals / Non-Goals

**Goals**
- Одна команда запускает все примеры и выдаёт итог по каждому: ok / FAIL / skip, время, путь к журналу.
- Код выхода скрипта — неуспех, если хоть один пример упал.

**Non-Goals**
- Запуск примеров в CI.
- Проверка вывода примеров сверх их собственных проверок.

## Decisions

### D-1. `scripts/run-examples.sh`, bash

- Сначала собирает все примеры одной командой (`cargo build --locked --workspace --all-features --examples` и пакет `axum-service`): ошибка сборки видна сразу, а время запуска не смешивается со временем сборки.
- Затем запускает примеры по порядку E-1…E-15 через `cargo run -q --locked`, каждый с ограничением времени (по умолчанию 300 с). На macOS нет `timeout`, поэтому через `perl -e 'alarm …; exec @ARGV'`. Вывод — в `target/examples-run/<имя>.log`.
- Аргументы — имена примеров, чтобы запустить часть: `scripts/run-examples.sh hello durable-store`.
- В конце — таблица итогов.

### D-2. Сервисы: свои адреса → Docker → пропуск

Для Kafka (E-12) и PostgreSQL (E-13, E-14), по каждому сервису отдельно:
1. Адрес из переменной окружения (или адрес по умолчанию) отвечает — используется он. Проверка порта средствами bash (`/dev/tcp`), без `nc`.
2. Не отвечает, но есть `docker` — `docker compose -f examples/docker-compose.yml up -d <сервис>`, ожидание порта до 60 с. Сервис, поднятый скриптом, им же и останавливается (`trap … EXIT`).
3. Нет ни того, ни другого — примеры сервиса помечаются `skip (no Kafka)` / `skip (no PostgreSQL)`.

Флаг `--require-services` превращает пропуск в неуспех: перед выпуском запускают с ним.

### D-3. Сценарий `axum-service`

1. Запуск в фоне, ожидание порта 3000 (до 60 с).
2. `curl`:
   - `POST /exports` → 202;
   - повторный `POST` того же id → 200 с `already running`: экспорт идёт 60 с;
   - `GET /exports/{id}` → 200;
   - `DELETE /exports/{id}` → 200 или 202.
3. SIGINT серверу, ожидание выхода с кодом 0 — отчёт об остановке печатается.

Любое расхождение — FAIL с указанием шага.

### D-4. Проверка самого скрипта в CI

Скрипт в CI не запускается, но задание «Check» прогоняет `shellcheck scripts/run-examples.sh`: shellcheck предустановлен на раннерах `ubuntu-latest`. Синтаксис и типовые ошибки ловятся без запуска.

### D-5. Порядок выпуска

- `examples/README.md`: раздел «Running all examples» — команда, флаг, итог.
- Спецификация 4.3 п. 8: «Перед выпуском примеры запускаются скриптом `scripts/run-examples.sh --require-services`; все — ok».
- Память о порядке выпуска (моя рабочая заметка) получает этот шаг.

### Спецификация

- 4.3 п. 8 (D-5); критерий из раздела 16 заявки — №93.
- Таблица статусов, версия спецификации.

## Risks / Trade-offs

- Порт 3000 занят — E-11 FAIL с понятным сообщением на шаге ожидания; порт в примере зашит, скрипт его не меняет.
- Kafka-пример в своём контейнере стартует дольше, чем ожидание порта: брокер принимает соединения раньше, чем готов. Пример сам ждёт группу; ограничение времени 300 с с запасом.

## Тестирование

- Локально: полный прогон с запущенными Kafka и PostgreSQL — все 15 ok; прогон без сервисов и без Docker — E-12…E-14 skip, с `--require-services` — неуспех; один пример по имени.
- `shellcheck` чистый; CI зелёный.
