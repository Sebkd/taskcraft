## Context

`Observer::on_event(&Event<'_>)` (`crates/taskcraft/src/observe.rs`) синхронен и вызывается на пути задачи через `Observers::emit`; паника перехватывается и пишется как WARN `observer/failed`. Так задумано (2.3.22): наблюдатель обязан быть быстрым. Наблюдатель, который пишет в сеть (отправка во внешнюю систему метрик, аудит), замедляет каждую задачу.

`Event<'a>` — 20 вариантов, все заимствуют данные библиотеки (`&str`, `&TaskId`, `&FinishReason`, `&StopReason`); `#[non_exhaustive]`, `Clone + Copy`. Передать событие в другой поток можно только копией.

## Goals / Non-Goals

**Goals**
- Адаптер, с которым медленный наблюдатель не замедляет задачи: событие копируется в ограниченный буфер, отдельный поток отдаёт его вложенному наблюдателю.
- Переполнение буфера не блокирует задачи: событие теряется, потери считаются и видны в журнале.

**Non-Goals**
- Изменение синхронного контракта `Observer` и `Event`.
- Гарантия доставки событий при остановке процесса.

## Decisions

### D-1. `observe::Buffered`

```rust
pub struct Buffered { /* sender, counters, name */ }
impl Buffered {
    /// `inner` receives the events on a thread of its own; at most
    /// `capacity` events wait for it.
    pub fn new(inner: impl Observer, capacity: usize) -> Result<Self, ConfigError>;
    /// Events lost to a full buffer so far.
    pub fn dropped(&self) -> u64;
}
impl Observer for Buffered { … }
```

- `on_event` копирует событие во внутренний собственный вид и делает `try_send` в `std::sync::mpsc::sync_channel(capacity)`. Он никогда не ждёт.
- Доставку ведёт отдельный поток ОС (`taskcraft-observer`), а не задача tokio. Наблюдатель синхронный и может блокироваться, так что занимать им рабочий поток рантайма нельзя. Ещё одна причина: адаптер можно создать вне рантайма.
- Поток восстанавливает `Event<'_>` из копии и вызывает вложенный наблюдатель. Паника перехватывается так же, как в `Observers::emit`: WARN `observer/failed`, событие теряется, поток живёт дальше.
- `capacity == 0` — `ConfigError::InvalidCapacity` (как у `InMemorySource`).
- `name()` — `Buffered(<имя вложенного>)`.
- Удаление адаптера (последней ссылки) закрывает канал. Поток отдаёт оставшиеся события и завершается, ждать его никто не будет.

### D-2. Собственный вид события — внутренний

`enum OwnedEvent` повторяет `Event` с собственными данными (`String`, `TaskId`, `FinishReason`, `StopReason`). У него есть `from(&Event)` и `as_event(&self) -> Event<'_>`. Тип не публичный: API пополняется одним `Buffered`. Сопоставление внутри пакета исчерпывающее. Поэтому новый вариант `Event`, не добавленный в копию, — ошибка компиляции, а не тихая потеря событий.

### D-3. Потери

- Счётчик `dropped` (`AtomicU64`) растёт на каждое потерянное событие.
- WARN `observer/dropped`, `observer events dropped: observer={}, count={}` — не чаще раза в 10 с на адаптер. `count` — потери с прошлой записи. Запись делает `on_event`, который застал полный буфер и истёкший интервал.

### D-4. Тесты (`crates/taskcraft/tests/observers.rs`)

1. **Медленный наблюдатель** (спит 200 мс на событие) за `Buffered` в мониторе. Время задачи не растёт: 20 задач проходят быстрее чем за 1 с, а наблюдатель получает их события позже.
2. **Порядок и полнота без переполнения:** события приходят все и в том же порядке, что у синхронного наблюдателя.
3. **Переполнение:** вложенный наблюдатель заблокирован, ёмкость 2, событий 10. `dropped() == 8`, одна запись WARN с `count=8`. После разблокировки приходят 2 первых события.
4. **Паника вложенного:** WARN `observer/failed`, следующие события доставляются.
5. `capacity == 0` — ошибка конфигурации.

## Risks / Trade-offs

- Копия события — выделения памяти на каждое событие (строки имени очереди и идентификатора). Это цена буфера, и платит её только тот, кто включил адаптер. Синхронный путь не меняется.
- События в буфере при выходе процесса теряются. Для медленного получателя (аудит, внешняя система) это ожидаемо, в документации сказано.
