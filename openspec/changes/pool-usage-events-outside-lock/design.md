## Context

`PoolHeld::count` (`crates/taskcraft/src/worker/pools.rs`) меняет счётчик `PoolClaim::in_use: Arc<Mutex<u32>>` и, не отпуская замка, вызывает наблюдателей (`Observers::emit`, событие `PoolUsage`). Так с 0.2.2 соблюдается правило 2.3.22 п. 1: «события одного пула идут по порядку, последнее — его текущая занятость». Цена — медленный наблюдатель держит замок, и каждое взятие и освобождение пула всеми очередями монитора ждёт его.

Правило требует порядка и верного последнего значения, но не события на каждое изменение.

## Goals / Non-Goals

**Goals**
- Наблюдатели пула вызываются без замка счётчика; изменение счётчика другим потоком не ждёт наблюдателя.
- Правило 2.3.22 п. 1 сохраняется: события пула идут по порядку, последнее — текущая занятость.

**Non-Goals**
- Изменение типа `Event::PoolUsage` (публичный API) и адаптера `metrics`.
- Асинхронная доставка событий (это BL-48 `async-observer`).

## Decisions

### D-1. Один отправитель на пул, промежуточные значения сливаются (отступление от заявки)

Заявка предлагала номер изменения в событии и отбрасывание старших номеров в адаптере `metrics`. Это меняет публичное событие, а пользовательские наблюдатели по-прежнему получали бы события не по порядку. Вместо этого — протокол «один отправитель»:

```text
change(f):
  под замком: value = f(value)
              если кто-то уже отправляет → выйти (он отправит и это значение)
              иначе reporting = true
  цикл:
    v = value; отпустить замок
    отправить PoolUsage(v)            ← без замка
    под замком: если value == v → reporting = false; выйти
                иначе → следующий круг с новым значением
```

- Отправляет в каждый момент не больше одного потока на пул: события пула идут по порядку.
- Отправитель выходит, только убедившись под замком, что отправленное значение — текущее: последнее событие равно занятости.
- Остальные потоки только меняют счётчик под коротким замком и не ждут наблюдателя.
- Промежуточные значения, пришедшие, пока отправитель занят, сливаются в одно — последнее. Для датчика это верно; правило 2.3.22 п. 1 событие на каждое изменение не требует.

Отправитель — поток, чьё изменение застало пул без отправителя. Он ждёт своих наблюдателей, как и сейчас — наблюдатели синхронны и выполняются на пути задачи. Ждёт он дольше одного вызова, только если другие потоки меняют пул, пока он отправляет; каждый лишний круг отправляет новое значение.

### D-2. `Gauge` — отдельный тип в `worker/pools.rs`

```rust
pub(crate) struct Gauge { state: Mutex<GaugeState> }
struct GaugeState { value: u32, reporting: bool }
impl Gauge {
    /// Applies `change`; reports through `report` unless another thread reports.
    pub(crate) fn change(&self, change: impl FnOnce(u32) -> u32, report: impl FnMut(u32));
}
```

`PoolClaim::in_use` становится `Arc<Gauge>`, а `PoolHeld::count` — вызовом `change` с отправкой `PoolUsage`. Тип не знает о наблюдателях, поэтому его можно проверить моделью.

### D-3. Модель `loom`

Как у реестра (`registry.rs`), под `cfg(taskcraft_loom)` `Gauge` берёт `loom::sync::Mutex`. Модельный тест: три потока меняют датчик (+1, +1, −1), отправка пишет значения в общий список и проверяет флагом, что две отправки не идут одновременно. После всех потоков последнее отправленное значение равно итогу, и параллельных отправок не было. CI уже запускает `cargo test -p taskcraft --release --lib loom`, так что новый тест попадает туда сам.

### D-4. Тест медленного наблюдателя

Модульный тест в `pools.rs` на настоящих потоках:
- наблюдатель на `PoolUsage` спит 300 мс;
- поток A берёт разрешение и становится отправителем;
- пока A спит, поток B берёт второе разрешение и возвращает его;
- B укладывается меньше чем в 100 мс, последнее событие равно итоговой занятости.

До исправления B ждёт замок около 300 мс, и тест падает — проверю это до правки.

Существующие проверки остаются:
- свойство «последнее событие пула — его занятость» (`tests/properties.rs`, 10 000 случаев в CI);
- `pools_stress.rs`, критерий №83.

Внутреннее изменение ядра, API тот же. Выпуск 0.3.2 — следующим выпуском.

## Risks / Trade-offs

- Наблюдатель видит не каждое промежуточное значение пула. Для датчика занятости это норма. Адаптер `metrics` пишет из `PoolUsage` только датчики занятости и размера (`observe/metrics.rs`, `series.pool(…).usage`), счётчиков по пулу нет.
- Отправитель при постоянной смене занятости делает несколько кругов. Каждый круг — новое значение, поэтому работы не больше, чем сейчас, когда событие идёт на каждое изменение.
