## Context

`QueueHandle::requeue` (0.2.1) возвращает задачу из «Ошибки» в очередь по идентификатору. Найти такие задачи можно только из хука `failed_task` или SQL-запросом к `taskcraft_tasks`. Статус одной задачи даёт `fetch_status` → `PgSource::status`, а строка состояния переводится в `TaskStatus` так: `StatusRow`, `crates/taskcraft-postgres/src/source.rs:163`, `:403`.

Схема хранится с версией (`MIGRATIONS` в `sql.rs`, сейчас 2). Индексы версии 2 — частичные: `due` (очередь, момент) для «В очереди»/«Отложена», `lease` для живых, `finished` (`updated_at`) для терминальных. Индекса, который отдавал бы задачи одной очереди в одном состоянии по порядку идентификаторов, нет. Первичный ключ `(queue, id)` даёт порядок, но фильтр по состоянию идёт перебором всей очереди. Сценарий «найти 10 упавших среди миллиона успешных за 7 дней хранения» тогда читает миллион строк на страницу.

`migrate` (`store.rs:485`): база новее библиотеки — ошибка старта `SchemaTooNew`.

## Goals / Non-Goals

**Goals**
- Список задач очереди в заданном состоянии, страницами, по возрастанию идентификатора, без пропусков и повторов.
- Страница читает не больше строк, чем отдаёт (по индексу).

**Non-Goals**
- Пакетная переотправка по фильтру — вызывающий код делает `requeue` по списку.
- Фильтры по времени, причине и прочему.

## Decisions

### D-1. `PgStore::tasks`

```rust
/// The tasks of `queue` in `state`, by id, at most `limit` (capped at 1000)
/// after `after` — the last id of the previous page.
pub async fn tasks(&self, queue: &str, state: TaskState, after: Option<&TaskId>, limit: u32)
    -> Result<Vec<TaskStatus>, PgStoreError>;
```

- Метод хранилища, а не ручки: список — служебная операция, для неё не нужна очередь в мониторе.
- `TaskStatus` — тот же, что у `fetch_status`. Перевод строки выносится из `PgSource::status` в общую функцию.
- `limit == 0` — пустой список; больше 1000 — 1000. Ошибки «плохой лимит» нет.
- Продолжение — по последнему идентификатору (`id > $after`), не по смещению: страницы не съезжают, пока задачи меняют состояние.

### D-2. Индекс — миграция 3

```sql
CREATE INDEX taskcraft_tasks_state ON taskcraft_tasks (queue, state, id);
```

Запрос: `WHERE queue = $1 AND state = $2 AND id > $3 ORDER BY id LIMIT $4`. Тест `EXPLAIN` в `sql.rs` проверяет, что используется этот индекс без полного прохода — как для захвата и очистки.

Цена записи. Каждая смена состояния обновляет и этот индекс. Обновления строки и сейчас не HOT: состояние входит в условия частичных индексов. Дополнительная работа — одна запись в индекс на смену состояния.

### D-3. Совместимость при выкатке — выбран вариант 1 (2026-10-13)

Миграция поднимает версию схемы до 3. Процесс 0.3.2 и старше при старте на такой базе получает `SchemaTooNew` и не стартует (уже работающие процессы не затронуты). При поэтапной выкатке 0.3.3 перезапуск старой версии после старта первой новой невозможен. Так было и при переходе на версию 2 в 0.2.1.

Варианты:
1. **Миграция 3 с индексом** (рекомендую). В `MIGRATION.md` и README пакета: «0.3.3 мигрирует схему до версии 3; откат на 0.3.2 и старше после старта 0.3.3 невозможен; выкатка — без отката, первый старт строит индекс и на это время задерживает запись в таблицу».
2. **Без индекса и без миграции.** Запрос идёт по первичному ключу с фильтром. Совместимо в обе стороны, но медленно на больших очередях.

### D-4. Тесты

- Интеграционный: 25 задач, из них 7 упавших, вперемешку с успешными и в двух очередях. Список «Ошибка» по 3 даёт 7 задач без повторов, по возрастанию, только своей очереди; продолжение после последней страницы пусто; лимит 0 — пусто.
- `EXPLAIN`: запрос списка использует `taskcraft_tasks_state`.
- Миграция: база версии 2 → 3, существующие тесты миграций (`legacy_schema_*`) расширяются проверкой нового индекса.

### D-5. Версия

Совместимое дополнение API пакета `taskcraft-postgres`. Выпуск 0.3.3. Схема — версия 3.

## Risks / Trade-offs

- D-3: выкатка без отката.
- Построение индекса на большой таблице задерживает запись на время первого старта. Это то же, что и при миграции 2; отражено в документации.
