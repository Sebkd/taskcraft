## Context

`PgStore::queue(name)` (`crates/taskcraft-postgres/src/store.rs:267`) создаёт для источника учёт `Held` (`store.rs:343`):
- `tasks` — задачи, которые выдал опрос этого источника;
- `notify` — канал уведомлений (`Notice`) его воркеру;
- `wake` — пробуждение его воркеров.

Учёт регистрируется в `Shared::queues: HashMap<Arc<str>, Arc<Held>>`, и повторный вызов с тем же именем **заменяет** запись. Регистрация читается в трёх местах:
1. `upkeep_once` (`store.rs:638`) продлевает аренды и читает запросы отмены только по задачам из зарегистрированного `Held`;
2. `listen` (`store.rs:516`) будит по уведомлению `LISTEN` только зарегистрированный `Held`;
3. при потере соединения уведомлений `listen` будит все `Held`.

Кроме того, `PgSource::insert` и `requeue` (`source.rs:94`, `:370`) будят только свой `Held`. Постановка через служебный источник без уведомлений (`notifications(false)`) не будит воркеры рабочего источника той же очереди: те увидят задачу на следующем опросе, до 30 с.

## Goals / Non-Goals

**Goals**
- Задачи, выданные любым источником очереди в процессе, продлеваются, и запросы отмены по ним доходят до воркера, который их исполняет.
- Постановка и повторный запуск через любой источник будят воркеры всех источников этой очереди в процессе.

**Non-Goals**
- Запрет повторного открытия: служебный источник на ту же очередь (статус, отмена, постановка) законен.
- Изменение публичного API.

## Decisions

### D-1. Учёт у каждого источника, регистрация — список (отступление от заявки)

Заявка предлагала один `Held` на имя. Но канал уведомлений (`Notices`) один на получателя: его забирает воркер одного источника (`PgSource::notices`, `source.rs:254`). При общем `Held` запросы отмены и потеря аренды по задачам второго источника, если на нём тоже работает воркер, уходили бы воркеру первого — то есть терялись бы.

Поэтому:
- у каждого источника свой `Held`, как сейчас;
- `Shared::queues` становится `HashMap<Arc<str>, Vec<Weak<Held>>>`: все живые источники имени;
- `queue()` добавляет свой учёт и заодно выбрасывает мёртвые ссылки этого имени;
- учёт живёт, пока жив источник (`Arc<Held>` в `PgSource`); после удаления источника его ссылка мертва, и обслуживание её пропускает.

Цель заявки и её критерий выполняются: аренды задач каждого источника продлеваются, уведомления доходят до исполняющего воркера.

### D-2. Пробуждение — всех источников имени

Одна внутренняя функция `wake_queue(&Shared, &str)` будит все живые `Held` имени. Её вызывают:
- `PgSource::insert` (вместо `self.held.wake.wake()`);
- `PgSource::requeue`;
- `listen` по уведомлению.

`poll` при отложенной задаче (`source.rs:94`) по-прежнему будит свой `Held`: это внутреннее дело одного опроса. Потеря соединения будит все `Held` всех имён.

### D-3. Обслуживание по снимку

`upkeep_once` берёт снимок живых `(имя, Arc<Held>)` под замком и отпускает замок до запросов к базе, как сейчас. Запрос продления выполняется для каждого источника отдельно. Источников одного имени обычно 1–2, поэтому объединять их в один запрос не нужно.

### D-4. Тест

Интеграционный тест в `crates/taskcraft-postgres/tests/store.rs`, хранилище с арендой (1,5 с) и без уведомлений:
1. монитор на источнике A простаивает 8 с, чтобы ожидание опроса выросло за 6 с;
2. открывается служебный источник B той же очереди, через него ставится задача `n = 4`, которая спит час;
3. задача «В работе» не позже чем через 1,5 с, то есть B разбудил воркер A (D-2);
4. B жив; ждём 3 срока аренды; второй процесс с арендой опрашивает очередь и получает «пусто»; задача по-прежнему «В работе» (D-1).

Сначала проверяю, что без исправления тест падает: на п. 3 или на п. 4.

### D-5. Версия

Исправление только в `taskcraft-postgres`, внутреннее. Входит в 0.3.1 при выпуске.

## Risks / Trade-offs

- Список вместо одной записи: мёртвые ссылки копятся, пока для этого имени снова не вызовут `queue()`. Это одна `Weak` на удалённый источник, к тому же обслуживание их пропускает. Чистить ещё и в обслуживании не нужно.
