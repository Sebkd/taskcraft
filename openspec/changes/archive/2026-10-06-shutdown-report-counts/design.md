# Design: Итог остановки считает только задачи, застигнутые остановкой

## Context

`run_worker` (`worker.rs`) держит исполняемые задачи в `JoinSet<TaskEnd>`. Завершившиеся задачи забираются `try_join_next_with_id` только в начале итерации цикла приёма — без подсчёта. При остановке `drain` забирает всё оставшееся и считает: `TaskEnd::Finished` → «завершено в срок», `TaskEnd::CancelledWaiting` → «отменено». Задачи, закончившиеся до сигнала, пока воркер спал между опросами или ждал слот, попадают в «завершено в срок».

---

## Goals / Non-Goals

**Goals:** «Завершено в срок» — только задачи, дошедшие до исхода после сигнала остановки или закрытия источника (уточнение 2.7.6, критерий №50).

**Non-Goals:** новые поля итога.

---

## Decisions

### Задача сама сообщает, застала ли её остановка

**Решение**:
- `ExecCtx` получает признак `draining: CancellationToken`. Воркер выставляет его, когда цикл приёма закончился по любой причине — сигнал остановки или закрытие источника, — до вызова `drain`.
- `finish` возвращает:
  - `TaskEnd::Finished`, если в момент исхода `draining` выставлен;
  - новый `TaskEnd::Before` — иначе.
- `Counts::add` пропускает `TaskEnd::Before`. `CancelledWaiting` возникает только от остановки, его подсчёт не меняется.

**Обоснование**: момент исхода фиксирует сама задача, а не порядок, в котором воркер забирает её из набора. Это не зависит от того, спал ли воркер, и одинаково работает для остановки и закрытия источника.

**Альтернативы**:
- В начале `drain` забрать все уже завершённые задачи без подсчёта — отклонено: задача, завершившаяся между сигналом и началом дренажа, была бы потеряна для итога, а тот же сон воркера дал бы гонку.

### Тесты, закрепившие старое поведение

**Решение**: два теста ожидают, что в «завершено в срок» попадут задачи, закончившиеся до сигнала:
- `tests/recovery.rs` — `completed == 4`;
- `tests/consumer_scenarios.rs` — `completed == 1`.

После уточнения 2.7.6 там 0; тесты исправляются с комментарием. Тест `shutdown_lets_running_tasks_finish_in_time` (задача в работе на момент сигнала) остаётся с `completed == 1` — это критерий заявки №1.

### Затронутые примеры

По таблице `examples/README.md` итог остановки печатают:
- E-6 `graceful-shutdown`;
- E-11 `axum-service`;
- E-3 `long-tasks-reject` (проверяет «отменено»).

E-6 и E-3 считают задачи, застигнутые остановкой, — значения не меняются. E-11 после исправления покажет 0 для задачи, отменённой до остановки. Все три прогнать вручную.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Задача завершилась одновременно с сигналом | Попадёт в итог или нет — по порядку атомарных операций | Граница неизбежна; оба исхода корректны по смыслу 2.7.6 |

## Изменения в коде

| Имя | Расположение | Изменение |
|-----|--------------|----------|
| `TaskEnd::Before` | `worker.rs` | Новый вариант |
| `ExecCtx::draining` | `worker.rs` | Признак «приём закончен» |
| `run_worker` | `worker.rs` | Выставить `draining` перед `drain` |
| `finish` | `worker.rs` | `Before`, если `draining` не выставлен |
| `Counts::add` | `worker.rs` | Пропускать `Before` |

## Тестирование

| Критерий | Тест |
|----------|------|
| №50 | Задача завершена и задача отменена по запросу до сигнала; воркер спит между опросами (интервал 30 с); сигнал → итог (0, 0, 0) |
| Заявки №1 | Существующий `shutdown_lets_running_tasks_finish_in_time` — (1, 0, 0) |
| Заявки №2 | Источник закрыт: одна задача до закрытия, одна при дренаже → «завершено в срок» = 1 |
| Заявки №3 | Все прочие тесты итога без изменений |
