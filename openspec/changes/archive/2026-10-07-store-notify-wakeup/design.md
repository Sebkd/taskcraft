## Context

- `PgSource` держит свой `WakeHandle` и будит им воркер своей очереди при постановке из **этого** процесса (`insert`) и при повторном запуске (`requeue`). Постановку из другого процесса воркер видит только следующим опросом. По умолчанию это до 30 с; в примерах ставили интервал 200 мс.
- `Shared.queues: HashMap<имя очереди, Arc<Held>>` — очереди этого процесса. `Held` делят источник и обслуживание.
- Задачи возвращаются в очередь тремя путями:
  - при старте процесса (`give_back`);
  - операцией администратора (`release_process`);
  - повторным запуском задачи с ошибкой (`requeue`).
- **sqlx 0.9 `PgListener`** (`connect_with(&pool)`, `listen`, `try_recv`):
  - при обрыве соединения `try_recv` возвращает `Ok(None)` или ошибку ввода-вывода;
  - следующий вызов переподключается и заново подписывается на каналы;
  - уведомления, пришедшие за время обрыва, теряются;
  - после закрытия пула — ошибка `PoolClosed`.

---

## Goals / Non-Goals

**Goals:** критерии №1–3.

**Non-Goals:** пробуждение в момент отложенной доставки — по-прежнему опросом.

---

## Decisions

### D-1. Когда хранилище отправляет NOTIFY

- **Как:** `SELECT pg_notify('taskcraft_tasks', <имя очереди>)` после успешной записи, отдельным оператором. Уведомление доставляется после фиксации транзакции.
- **Отправляет, когда в очереди появилась работа сейчас:**
  - постановка без момента доставки;
  - `requeue`;
  - возврат задач при старте (`give_back`) — по уведомлению на каждую очередь;
  - `release_process` — тоже по каждой очереди.
- **Не отправляет** при отложенной постановке и отложенном повторе. Заявка называет отложенный повтор, но такая задача станет доступна позже: уведомление разбудит воркеры, а опрос ничего не найдёт. До момента работы нет, это и есть граница Non-Goals.

### D-2. LISTEN

- **Пробуждение.** `WakeHandle` очереди переезжает из `PgSource` в `Held`. Так его видят и источник, и слушатель уведомлений.
- **Задача-слушатель**, порождается при старте хранилища (рядом с `upkeep`):
  - `PgListener::connect_with(&pool)`, `listen("taskcraft_tasks")`;
  - в цикле `try_recv`; имя очереди из уведомления → `wake()` у её `Held`, если у этого процесса такая очередь есть.
- **Где живёт.** Задача держит слабую ссылку на `Shared`: хранилище удалили — задача завершается. Отменяется вместе с `upkeep` в `Drop` для `Shared`.
- **Ошибка подключения при старте** — ошибка старта хранилища: база та же, что для всего остального.
- **Обрыв** — `Ok(None)` или ошибка, кроме закрытия пула (критерий №3):
  - журнал WARN `source/notify_lost`: `task store notifications lost, reconnecting: process_id={}, error={}`;
  - будятся **все** очереди процесса, потому что пропущенные уведомления потеряны;
  - пауза 1 с;
  - снова `try_recv`, который переподключается.
  - Пока соединения нет, работает опрос по стратегии.
- **Закрытие пула** (`PoolClosed`) — слушатель тихо завершается.
- **Свои уведомления** процесс получает тоже. Вторая побудка своей очереди безвредна: опрос найдёт задачу или пустоту.

### D-3. Настройка

- `PgStoreBuilder::notifications(bool)`, по умолчанию `true`.
- `false` — ни `LISTEN`, ни `NOTIFY`, поведение 0.1–0.2 (критерий №2). Это для пулеров соединений в режиме транзакций (PgBouncer), где `LISTEN` не работает.
- В README пакета: с уведомлениями стратегию опроса можно оставить по умолчанию — растущие паузы до 30 с работают как страховка.

### D-4. Тесты (пакет хранилища, база через `TASKCRAFT_POSTGRES_URL`)

- **Стратегия процесса B** во всех трёх тестах: `FirstOf([Wake, Interval(60 с)])`. Без пробуждения задачу он увидит не раньше чем через минуту.
- **Критерий №1:** A и B — разные хранилища и процессы. A ставит задачу, B выполняет её быстрее 5 с.
- **Критерий №2:** у B уведомления выключены. Задачи нет и через 3 с.
- **Критерий №3:**
  - пул B открыт со своим `application_name`, его соединение `LISTEN` обрывается через `pg_terminate_backend`;
  - соединения других тестов, идущих параллельно, не задеты;
  - есть WARN `source/notify_lost`;
  - после переподключения новая постановка из A снова будит B быстрее 5 с.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Ещё одно соединение на процесс | Пул базы меньше на одно соединение | `PgListener` держит своё соединение; в README пакета |
| Очень частые постановки | Поток уведомлений | NOTIFY дёшев, совпадающие уведомления в одной транзакции PostgreSQL сливает; воркер, будучи занят, пробуждение просто запоминает |

## Затронутые примеры

E-14 `leases-failover` и E-13 `durable-store` задают `PollStrategy::Interval(200 мс)` с комментарием «чужая работа видна только опросом». Интервал убирается: остаётся стратегия по умолчанию, комментарий меняется. Захват по истёкшей аренде всё равно идёт опросом, поэтому в E-14 интервал для этого сохраняется — с новым комментарием.
