## Context

Все кирпичи для воркера уже есть:

- `Source`, `Codec`, `InMemorySource`, `WakeSignal` — контракт источника;
- `task_fn`, `run_attempt`, `Outcome` — обработчик и исход;
- `PollStrategy`, `Poller::wait` — прерываемый сон;
- `Task`, `Lifecycle`, `TaskState`, `FinishReason` — модель;
- `taskcraft::testing` — харнесс со сценариями `Runner`.

Эта заявка собирает из них очередь, воркер и монитор: цикл приёма по 2.4.2, супервизию (2.3.12), отравленные сообщения (2.3.13), остановку (2.3.14) и итог остановки (2.7.6). Здесь же появляются первые записи журнала в формате 2.9: `event`, `action`, `message` с `ключ=значение`; спаны попыток уровня DEBUG (4.4.1).

Границы с соседними заявками. Критерии этой заявки в части, которая зависит от ещё не сделанного, переходят туда:

| Что | Где | Что делает воркер сейчас |
|-----|-----|--------------------------|
| Исход «повторить» и паузы | `retry-policy` | Без политики повторов максимум попыток — 1, умолчание 2.8. «Повторить» сразу даёт «Ошибка» с причиной «попытки исчерпаны». Часть критериев №21 и №39 про «паузу повтора» проверяется там |
| «Отложить» без поддержки источника | `retry-policy` (правило 2.3.6) | Здесь — только отложенный повтор источником (`Source::defer`). Без поддержки источника «отложить» исполняется как «повторить» с пустым лимитом, то есть «Ошибка». Деградацию с паузой в процессе добавит `retry-policy` |
| Политика переполнения и лимит ожидания | `overflow-policy-and-resource-pools` | Слоты — семафор на лимит конкурентности. Воркер берёт слот **до** опроса, то есть при занятых слотах ждёт: это политика «ждать» с нулевым лимитом ожидания |
| Хук восстановления и состояние «Запуск» с ним | `ownership-and-recovery` | Состояние «Запуск» есть, но проходится сразу (переход 2.4.2.2). Критерий заявки №1 (остановка во время хука, переход 2.4.2.11) переходит туда вместе с хуком |
| Наблюдатель и события | `observability` | Части критериев №2 и №9 про события наблюдателя проверяются там; журнал — здесь |
| Признак отмены как извлекаемое значение | `task-registry` | У каждой задачи уже есть свой токен отмены; извлекать его в обработчике научит `task-registry`. Пока что после льготного времени задача прерывается принудительно |

## Goals / Non-Goals

**Goals:**

- `Queue` с построителем: имя, источник, кодек, сервис-обработчик, лимит конкурентности, момент ack, стратегия опроса, льготное время отмены, реестр метаданных, общие данные, хук dead-letter.
- `Monitor`: регистрация очередей (уникальные имена), таймаут остановки, задержки перезапуска, `run(stop)` → `ShutdownReport`.
- Воркер по 2.4.2:
  - три ответа опроса;
  - неблокирующая передача задачи на исполнение;
  - супервизия с ростом задержки и сбросом;
  - отравленные сообщения через хук dead-letter;
  - ack по моменту очереди или задачи, ошибка ack ведёт к перезапуску, но не меняет исход;
  - дренаж и итог остановки.
- Журнал по 2.9 и спаны попыток уровня DEBUG по 4.4.1.
- Реализация `Runner` из харнесса поверх настоящего воркера; сценарии `empty_never_ends_worker`, `boxed_abort_is_not_retried`, `poison_does_not_stop_worker` проходят.

**Non-Goals:** см. таблицу границ выше.

## Decisions

### Очередь — построитель с проверкой; воркер — обобщённая функция

**Решение**: `Queue::builder(name, source, codec, service)` с методами:

| Метод | Значение | По умолчанию |
|-------|----------|--------------|
| `concurrency(n)` | лимит конкурентности | 1 |
| `ack_point(p)` | момент ack | «после приёма» |
| `poll_strategy(s)` | стратегия опроса | по умолчанию 2.8 |
| `cancel_grace(d)` | льготное время отмены | 30 с |
| `metadata_registry(r)` | реестр метаданных | пустой |
| `shared_data(d)` | общие данные | пустые |
| `dead_letter(hook)` | хук dead-letter | журнал ERROR без содержимого |

`build() -> Result<Queue, ConfigError>`. Проверки 2.10:
- имя не пусто;
- лимит ≥ 1;
- стратегия корректна (`PollStrategy::validate`);
- льготное время > 0.

Ограничения: `S: Source`, `C: Codec<Args, S::Message>`, `Svc: tower::Service<TaskRequest<Args>, Response = Outcome> + Clone + Send + 'static` с `Svc::Error: Into<BoxError>` и `Svc::Future: Send`, `Args: Send + 'static`. Воркер — обобщённая асинхронная функция над этими типами; монитор хранит очереди стёртыми до `Box<dyn FnOnce(WorkerContext) -> BoxFuture<'static, QueueReport>>`.

**Обоснование**: 2.10 — ошибки конфигурации до исполнения. Стирание типов только на границе монитора: в одном мониторе очереди с разными аргументами, источниками и обработчиками, но внутри воркера всё мономорфно.

**Альтернативы**:
- `dyn Source` — отклонено: трейт с `impl Future` не объектно-безопасен (решение `source-contract`).

### Хук dead-letter получает копию сообщения

**Решение**:
- `dead_letter(hook)` доступен, только если `S::Message: Clone`: построитель сохраняет вместе с хуком функцию копирования.
- Перед декодированием воркер копирует сообщение — только когда хук задан.
- Хук получает `DeadLetter { queue, message, error }`.
- После хука сообщение подтверждается, даже если хук паникнул (2.2.4): вызов хука идёт под `catch_unwind`.

**Обоснование**: 2.3.13 — хук получает сообщение и причину, а `Codec::decode` забирает сообщение по значению. Копирование только при заданном хуке не стоит ничего очередям без него. Сообщения Kafka и хранилища — байты, их копия дешёвая.

**Альтернативы**:
- Декодирование по ссылке — отклонено: меняет контракт `Codec` ради редкого пути.

### Квитанция источника становится `Clone`

**Решение**: в трейте `Source` у `Receipt` добавляется ограничение `Clone`.

**Обоснование**: при моменте ack «после приёма» квитанция уходит в ack до исполнения, а для «отложить» источником она нужна снова. Квитанции на деле — номер выдачи, смещение, ключ строки; `Delivery` уже `Copy`. Изменение публичного контракта до первой рабочей версии допустимо.

### Цикл воркера

**Решение**: один асинхронный цикл на очередь. Исполнение попыток — в `tokio::task::JoinSet` этого воркера.

1. **«Запуск» → «Приём»** (2.4.2.1, 2.4.2.2); журнал `worker/started`.
2. **Слот.** Занять слот (`Semaphore::acquire_owned`) под `select!` с остановкой.
3. **Опрос.** `mark_seen()` на сигнале, `poll()` под `select!` с остановкой.
4. **Ответ:**
   - **Ошибка** → «Перезапуск» (2.4.2.5):
     - журнал `source/failed` с `restart_in`;
     - задержка `min(начальная × 2^(n−1), максимальная)`;
     - сон под остановкой;
     - журнал `worker/resumed` (2.4.2.9).
     - n — ошибки подряд, сбрасывается первым успешным опросом (2.3.12).
   - **«Пусто»** → отпустить слот, «Ожидание», `Poller::wait` (2.4.2.3, 2.4.2.4). `Stopped` → «Дренаж».
   - **«Закрыт»** → журнал `source/closed`, «Дренаж» (2.4.2.7).
   - **Задача:**
     1. `poller.reset()`, копия для dead-letter, декодирование.
     2. Ошибка декодирования → хук или журнал `source/message_dropped`, ack, далее.
     3. Принять: время приёма, журнал DEBUG `task/accepted`.
     4. Момент ack — задачи или очереди. «После приёма» → ack сразу.
     5. Запуск исполнения в `JoinSet` со слотом, токеном отмены задачи и квитанцией (для ack «после завершения» и для «отложить»).
     6. Воркер **не ждёт** исполнения и идёт к следующему опросу.
5. **Ошибки ack** из исполнений приходят в цикл через канал. В «Приёме» и «Ожидании» они ведут в «Перезапуск» (2.4.2.5, 2.4.2.12); исход задачи не меняется (2.2.5). Канал проверяется в начале каждой итерации и в ожидании.
6. **«Дренаж» → «Остановлен»** — по алгоритму остановки ниже; журнал `worker/stopped` с причиной (2.4.2.8).

**Обоснование**:
- Переходы 2.4.2 один к одному.
- `JoinSet` даёт и ожидание, и принудительное прерывание (`abort_all`) всех попыток очереди.
- Канал ошибок ack отделяет исполнение от решения о перезапуске: перезапуск — состояние цикла приёма, а не задачи.

### Исполнение одной задачи

**Решение**: функция `execute`:

1. «Принята» → «В работе» (`Lifecycle`), номер попытки +1.
2. Спан `taskcraft.attempt` уровня DEBUG с `queue`, `task_id`, `attempt`; журнал DEBUG `task/started`.
3. `run_attempt(&mut service, request)` — паника и ошибки сервиса уже переведены в исход.
4. Если токен отмены задачи сработал к моменту исхода и исход не «паника» → «Отменена» по остановке (2.3.15 п. 4).
5. Иначе по исходу:

| Исход | Итог |
|-------|------|
| `Success` | «Завершена» |
| `Abort` | «Ошибка» |
| `Panic` | «Паника» |
| `Retry` | «Ошибка» с причиной «попытки исчерпаны» (максимум 1, см. границы) |
| `Defer` при поддержке источника | `codec.encode` и `source.defer(квитанция, сообщение, сейчас + задержка)` → «Отложена»; ошибка `defer` → «Ошибка» |
| `Defer` без поддержки | как `Retry` |

6. Журнал:
   - ERROR `task/panicked` и `task/failed`;
   - DEBUG `task/finished` с исходом.
7. Ack «после завершения»:
   - после «Завершена», «Ошибка», «Паника»;
   - **не** после «Отменена» остановкой (2.2.7) и не после «Отложена» — квитанцию забрал `defer`.
   - Ошибка ack → в канал ошибок воркера.
8. Слот освобождается вместе с задачей исполнения — при любом исходе, включая принудительное прерывание (инвариант 1.3.6).

### Остановка и итог

**Решение** (2.3.14):

1. Сигнал → воркер прекращает опросы, журнал `shutdown/started` (один раз в мониторе).
2. Задачи в работе **не** получают признак отмены; ждём их до таймаута остановки.
3. Таймаут → `cancel()` на токенах всех оставшихся задач, ждём льготное время.
4. Не уложились → `JoinSet::abort_all()`.
5. Итог очереди `QueueReport`:
   - `reason` — `Shutdown` или `SourceClosed(причина)`;
   - `completed` — задачи, дошедшие до исхода до таймаута;
   - `cancelled` — получившие признак отмены;
   - `aborted` — прерванные принудительно, часть `cancelled`.
6. `ShutdownReport` монитора — список отчётов очередей; журнал `shutdown/finished` с суммами.
7. Закрытие источника («закрыт») ведёт очередь в тот же дренаж, но без таймаута остановки: задачи дорабатывают сами.

**Обоснование**: 2.3.14 пп. 4–8, модель 2.7.6, критерий №21 в части задач в работе.

### Журнал и спаны

**Решение**:
- `tracing` в основные зависимости.
- Все записи — макросами с полями `event` и `action` и сообщением `фраза: ключ=значение…` по таблице 2.9.
- Значения с пробелами — в кавычках, через `Debug`-печать строки: она уже даёт кавычки и экранирование.
- Аргументы и метаданные задачи не пишутся (инвариант 1.3.18).
- Спан попытки — `tracing::debug_span!`.

**Обоснование**: 2.9, 4.4.1 и соглашение первого потребителя.

### Уточнения при реализации

- **`Args: Clone` у очереди.** Каждой попытке нужна своя копия аргументов: для «отложить» источником задача кодируется заново после попытки, а будущие повторы в процессе (`retry-policy`) запускают обработчик снова.
- **Тип аргументов выводится из кодека.** `Queue::builder` требует `C: Codec<Args, S::Message>`, поэтому тип аргументов известен сразу, а не только при регистрации в мониторе.
- **`CancellationToken` реэкспортирован из корня пакета.** Это сигнал остановки `Monitor::run`, и пользователю не нужна прямая зависимость от `tokio-util`.
- **`tokio` с `rt` — в основных зависимостях** (`JoinSet`), поэтому возможность `test-util` снова пустая.
- **Новая запись журнала `source/dead_letter_failed`** — хук dead-letter паникнул (сценарий 2.2.4). Добавляется в таблицу 2.9 при apply.
- **В номера задач `JoinSet` вписаны идентификаторы задач**, чтобы запись `task/aborted` несла `task_id` по 2.9.
- **`tracing-subscriber` — dev-зависимость** для перехвата журнала в тестах.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Слот берётся до опроса | При занятых слотах воркер не опрашивает источник | Это «ждать» с нулевым лимитом ожидания; лимит ожидания и «отказать» добавит `overflow-policy-and-resource-pools` |
| «Повторить» до `retry-policy` — сразу «Ошибка» | Поведение до политики повторов беднее спецификации | Совпадает с умолчанием 2.8 (максимум попыток 1); задокументировано |
| Принудительное прерывание без кооперативной отмены в обработчике | Обработчик не может завершиться сам за льготное время | Извлекаемый признак отмены — в `task-registry` |
| Изменение `Source::Receipt` на `Clone` | Ломает собственные источники с не-`Clone` квитанцией | Версия 0.x, рабочих выпусков ещё нет |

```

                                  │                                               ▼
```

## Детали реализации

### Алгоритмы

```
задержка перезапуска(n) = min(начальная × 2^(n−1), максимальная), n ≥ 1

drain(join_set, tokens, shutdown_timeout, grace):
  ждать опустошения join_set не дольше shutdown_timeout → завершившиеся = completed
  если пусто → итог
  cancel всех оставшихся токенов; cancelled = число оставшихся
  ждать не дольше grace
  если не пусто → aborted = число оставшихся; abort_all; дождаться
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| Хук dead-letter паникнул | Журнал ERROR, сообщение всё равно подтверждается (2.2.4) |
| Ack после декодирования отравленного сообщения не удался | Ошибка ack → «Перезапуск» |
| Ack «после приёма» не удался | Задача всё равно исполняется; «Перезапуск» после её запуска |
| Сигнал остановки во время задержки перезапуска | «Дренаж» сразу (инвариант 1.3.7) |
