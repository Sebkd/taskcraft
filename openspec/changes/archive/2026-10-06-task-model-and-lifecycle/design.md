## Context

Первая заявка с кодом. Рабочее пространство уже есть (`bootstrap-workspace`): пакет `crates/taskcraft` содержит только `src/lib.rs` с документацией пакета. Общие правила линтера запрещают `unsafe`, требуют документации для всего публичного (`missing_docs`) и `Debug` для публичных типов (`missing_debug_implementations`). Сложные типы не разрешены глобально (A-9).

Заявка вводит публичные типы, на которых строятся остальные контракты:

- задачу;
- её состояния и допустимые переходы;
- метаданные с реестром типов;
- результат постановки, статус задачи и причины исходов.

Исполнения в этой заявке нет: переходы будет вызывать воркер (`worker-loop-and-supervision`), извлекать метаданные — обработчик (`handler-error-classification`).

Источники требований — спецификация `openspec/specs/taskcraft/taskcraft.md`:

- 1.2 — глоссарий: документация типов;
- 2.4.1 — 9 состояний, 13 переходов, запрещённые переходы;
- 2.7.1–2.7.4 — модели;
- 2.3.17 — метаданные;
- 2.11.4 — причины;
- критерий №29 — неизвестные имена метаданных не теряются при повторном кодировании.

## Goals / Non-Goals

**Goals:**

- Тип задачи с идентификатором, аргументами, метаданными, счётчиками попыток и повторов, переопределением момента ack и временем приёма.
- Состояния задачи и проверка переходов строго по таблице 2.4.1: переход вне таблицы отклоняется, состояние не меняется.
- Метаданные: одно значение на тип, без кодирования внутри процесса; реестр типов со стабильными именами; кодирование во внешнее представление 2.7.2 и обратно; ленивый разбор; сохранение неизвестных имён; зарезервированное имя `trace_parent`.
- Результат постановки (2.7.3), статус (2.7.4), причины исходов (2.11.4).

**Non-Goals:**

- Guard-условия переходов (свободный идентификатор, слот, повторы остались): это правила 2.3.x, их проверяют заявки, которые эти переходы выполняют. Здесь проверяется только допустимость пары «из → в».
- Извлечение метаданных обработчиком и исход «прервать» при их отсутствии — `handler-error-classification`.
- Сериализация аргументов задачи (кодек) — `source-contract`.
- Тип метаданных для `trace_parent` и его связь со спанами — `observability`. Здесь имя только резервируется.

## Decisions

### Модули ядра и плоский публичный интерфейс

**Решение**: код в приватных модулях `task`, `state`, `metadata`, `status`, `error` внутри `crates/taskcraft/src`. Публичные типы реэкспортируются из корня пакета (`taskcraft::Task`, `taskcraft::TaskState` и т. д.).

**Обоснование**: потребитель не должен знать раскладку файлов. Перестановка модулей тогда не ломает интерфейс, а `unreachable_pub` подсвечивает случайно открытое.

**Альтернативы**:
- Публичные модули (`taskcraft::task::Task`) — отклонено: раскладка становится частью интерфейса, а пакет маленький.

### Идентификатор задачи — строковый newtype с генерацией UUID v4

**Решение**: `TaskId` — обёртка над `String`.
- Конструкторы: `TaskId::new(impl Into<String>)` и `TaskId::generate()` (UUID v4 в каноническом текстовом виде).
- Трейты: `Display`, `AsRef<str>`, `From<String>`, `From<&str>`, `Clone`, `Eq`, `Hash`, `Ord`, `Serialize`, `Deserialize` (прозрачно как строка).
- Задача без явного идентификатора получает сгенерированный при создании.

**Обоснование**: глоссарий 1.2 говорит, что идентификатор — строка, а если он не задан, библиотека генерирует UUID v4. Newtype не даёт перепутать идентификатор задачи с другой строкой. Строка, а не `Uuid`, потому что идентификаторы потребителя и ключи Kafka произвольны.

**Альтернативы**:
- `Uuid` как тип идентификатора — отклонено: потребитель задаёт идентификаторы сам, и они не обязаны быть UUID.
- Генерировать идентификатор лениво при постановке — отклонено: у задачи всегда должен быть идентификатор, иначе `Option` расползается по всему коду.

### Задача: `Task<Args>` с построителем по значению

**Решение**: поля приватные, чтение — через методы.

| Поле | Тип | Чтение |
|------|-----|--------|
| `id` | `TaskId` | `id()` |
| `args` | `Args` | `args()`, `into_args()` |
| `metadata` | `Metadata` | `metadata()`, `metadata_mut()` |
| `attempt` | `u32` | `attempt()`; 0 до первой попытки |
| `retries` | `u32` | `retries()` |
| `ack_point` | `Option<AckPoint>` | `ack_point()` |
| `accepted_at` | `Option<SystemTime>` | `accepted_at()`; заполняется при переходе 2.4.1.1 |

- Построение: `Task::new(args)`, затем `with_id`, `with_meta::<T>(value)`, `with_ack_point(AckPoint)`. Каждый метод принимает `self` и возвращает `Self` с `#[must_use]`.
- Изменение счётчиков и времени приёма — методы `pub(crate)`: их меняет только движок.

**Обоснование**: модель 2.7.1. Приватные поля сохраняют инварианты: счётчики не уменьшаются, время приёма ставит движок. Построитель по значению читается как спецификация: «задача из аргументов, дополненная идентификатором и метаданными».

**Альтернативы**:
- Публичные поля — отклонено: потребитель мог бы подделать номер попытки.
- Отдельный тип-построитель — отклонено: лишняя сущность при всего трёх необязательных полях.

### Момент ack — enum `AckPoint`

**Решение**: `AckPoint { OnAccept, OnCompletion }` с `Copy`, `Eq` и `Default = OnAccept` (умолчание спецификации 2.8).

**Обоснование**: поле модели 2.7.1. Правила применения (2.3.9, 2.3.10) реализует `source-contract`.

### Состояния — enum `TaskState`; проверка переходов — по таблице пар

**Решение**:
- `TaskState`: `Queued`, `Accepted`, `Running`, `RetryWaiting`, `Deferred`, `Succeeded`, `Failed`, `Panicked`, `Cancelled`. Трейты `Copy`, `Eq`, `Hash`, `Debug`, `Display` (русское название из спецификации не используется; `Display` — англ. имя в нижнем регистре: `queued`, `accepted`, …).
- `TaskState::is_terminal()` — `Succeeded`, `Failed`, `Panicked`, `Cancelled` (глоссарий «терминальный статус»).
- `TaskState::ends_in_process()` — терминальные плюс `Deferred` («да (для процесса)» в 2.4.1).
- `TaskState::can_transition_to(self, to) -> bool` — проверка по константной таблице из 13 пар.
- Отдельный тип `Lifecycle` хранит текущее состояние:
  - `Lifecycle::queued()` — начало перехода 2.4.1.12;
  - `Lifecycle::accepted()` — начало перехода 2.4.1.1;
  - `advance(&mut self, to) -> Result<(), InvalidTransition>` — при недопустимом переходе возвращает ошибку и **не** меняет состояние.

**Обоснование**: критерий заявки №1. Таблица пар — прямое отражение 2.4.1, её легко сверить со спецификацией. Начальные переходы выражены конструкторами, поэтому «из ниоткуда в Running» выразить нельзя. Состояния `Deferred` и терминальные переходов наружу не имеют — это и есть «запрещённые переходы».

| # | Из | В |
|---|----|---|
| 2.4.1.1 | (начало), `Queued` | `Accepted` |
| 2.4.1.2 | `Accepted` | `Running` |
| 2.4.1.3 | `Accepted` | `Cancelled` |
| 2.4.1.4 | `Running` | `Succeeded` |
| 2.4.1.5 | `Running` | `RetryWaiting` |
| 2.4.1.6 | `Running` | `Failed` |
| 2.4.1.7 | `Running` | `Panicked` |
| 2.4.1.8 | `Running` | `Cancelled` |
| 2.4.1.9 | `Running` | `Deferred` |
| 2.4.1.10 | `RetryWaiting` | `Accepted` |
| 2.4.1.11 | `RetryWaiting` | `Cancelled` |
| 2.4.1.12 | (начало) | `Queued` |
| 2.4.1.13 | `Queued` | `Cancelled` |

**Альтернативы**:
- Состояния как типы (typestate) — отклонено: состояние задачи хранится в реестре и запрашивается по идентификатору во время исполнения, а typestate проверяет порядок только во время компиляции и не даёт хранить задачи в разных состояниях в одной коллекции.
- statecraft-fsm для жизненного цикла задачи — отклонено: guard'ы и побочные эффекты переходов живут в разных компонентах движка (воркер, реестр, источник), а не в обработчиках одного автомата. Нужна только проверка допустимости пары.

### Метаданные: типизированная карта плюс сырые значения

**Решение**: `Metadata` хранит две части.
- **Типизированные значения:** `TypeId → Box<dyn MetaValue>`, где `MetaValue` — внутренний объектно-безопасный трейт (клонирование в `Box`, доступ как `Any`, имя типа для `Debug`). Публично значения требуют `T: Clone + Send + Sync + 'static`.
- **Сырые значения:** `BTreeMap<String, serde_json::Value>` — пришедшие из внешнего представления и ещё не разобранные.

Операции:

| Операция | Поведение |
|----------|-----------|
| `insert::<T>(value)` | Заменяет прежнее значение типа (2.3.17 п. 1) |
| `get::<T>() -> Option<&T>` | Только типизированные значения, без разбора |
| `remove::<T>()` | Удаляет типизированное значение |
| `contains::<T>()` | Есть ли типизированное значение |
| `resolve::<T>(&MetadataRegistry) -> Result<Option<T>, MetadataError>` | Ленивый разбор, см. ниже |

`resolve` работает так:
1. Есть типизированное значение → его клон.
2. Иначе тип есть в реестре и под его именем есть сырое значение → разобрать. Неудача → `MetadataError::Unparsable { name, type_name, reason }`, значение по умолчанию не подставляется.
3. Иначе → `Ok(None)`.

`Metadata` реализует `Clone`, `Default` и ручной `Debug` (имена типов и сырые имена, **без значений** — инвариант 1.3.18).

**Обоснование**:
- 2.3.17 п. 2: внутри процесса значения хранятся как есть.
- п. 5: разбор при извлечении, а не при опросе.
- п. 6: неизвестные имена хранятся сырыми и записываются обратно.

JSON как сырое представление совпадает с кодеком по умолчанию (глоссарий «Кодек») и моделью 2.7.2. `Debug` без значений не даёт секретам из метаданных попасть в журнал.

**Альтернативы**:
- `http::Extensions` — отклонено: нет `Clone` для значений, нет сырой части и тянет зависимость `http`.
- Разбирать всё сразу при декодировании — отклонено: нарушает 2.3.17 п. 5. Неразборное значение превращало бы сообщение в отравленное.
- Строковый «ключ — значение», как в apalis — отклонено решением Q-10.

### Реестр типов метаданных

**Решение**: `MetadataRegistry`.
- Регистрация: `register::<T>(name) -> Result<Self, ConfigError>`, где `T: Serialize + DeserializeOwned + Clone + Send + Sync + 'static`.
- Хранит `TypeId → (name, encode)` и `name → (TypeId, decode)`; `encode` и `decode` — указатели на мономорфизированные функции.
- Ошибки регистрации: `ConfigError::DuplicateMetadataName`, `DuplicateMetadataType`, `ReservedMetadataName` (для `trace_parent`). Тексты — из 2.10: "duplicate metadata name", "reserved metadata name".
- Кодирование: `encode(&Metadata) -> Result<serde_json::Map<String, Value>, MetadataError>`.
  - Типизированные значения кодируются под зарегистрированными именами. Незарегистрированный тип → `MetadataError::UnregisteredType { type_name }` (сценарий 2.2.10).
  - Сырые значения добавляются как есть, если под тем же именем нет типизированного: типизированное новее.
- Декодирование: `decode(Map) -> Metadata` — всё кладётся в сырую часть без разбора.

**Обоснование**: 2.3.17 пп. 3, 4, 8; критерий заявки №3 и критерий спецификации №29. Указатели на функции не требуют `dyn` с дженериками и держат типы простыми (A-9).

**Альтернативы**:
- Глобальный реестр (статический) — отклонено: у разных очередей могут быть разные наборы типов, а глобальное состояние мешает тестам.
- Ошибка регистрации паникой — отклонено: 2.10 требует ошибку конфигурации.

### Результат постановки, статус, причины

**Решение**:
- `PushOutcome` с `#[must_use]`: `Enqueued { id }`, `AlreadyRunning { id, state }`, `AlreadyFinished { id, state }`, `Rejected { id, reason: RejectReason }`. `RejectReason` пока один вариант — `SourceFull`; помечен `#[non_exhaustive]`.
- `TaskStatus`: поля модели 2.7.4. Время — `SystemTime`: статус отдаётся во внешние системы. Поля открыты для чтения через методы; создаёт его движок (`pub(crate)` конструктор).
- `FinishReason` (`#[non_exhaustive]`):
  - `Handler(String)`, `AttemptsExhausted`;
  - `MissingMetadata { type_name }`, `UnparsableMetadata { name, type_name }`;
  - `AttemptTimeout`, `Panic(String)`;
  - `CancelledByUser`, `CancelledByShutdown`, `LeaseLost`, `RejectedOverflow`.
  - `Display` — короткая фраза без значений аргументов.

**Обоснование**: модели 2.7.3, 2.7.4 и таблица 2.11.4. `non_exhaustive` позволяет добавлять варианты в следующих заявках без ломки потребителей.

### Ошибки — `thiserror`

**Решение**: публичные `ConfigError`, `MetadataError`, `InvalidTransition` через `thiserror`. Перечисления ошибок помечены `#[non_exhaustive]`.

**Обоснование**: так же сделано в statecraft-fsm; спецификация 2.11 различает ошибки конфигурации и задачи.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| `T: Clone` для метаданных | Тип без `Clone` нельзя положить в метаданные | Метаданные — небольшие сопутствующие сведения; `Arc<T>` покрывает тяжёлые случаи |
| Новые зависимости (`serde`, `serde_json`, `thiserror`, `uuid`) требуют записей cargo-vet | Задание supply-chain упадёт без них | Импортированные аудиты Google и Mozilla покрывают их; непокрытое — `cargo vet regenerate exemptions` в этой же заявке |
| Сырое значение в JSON | Источник с другим кодеком должен переводить метаданные через JSON | Кодек по умолчанию — JSON; другие кодеки — забота `source-contract` |
| `SystemTime` в статусе может идти назад при коррекции часов | Время в статусе неточно | Время в статусе только для отчёта; таймеры движка используют монотонное время tokio |

## Детали реализации

### Алгоритмы

```
encode(metadata, registry):
  out = {}
  для каждого типизированного значения v типа T:
    запись = registry.по_типу(T); нет → ошибка UnregisteredType(имя типа T)
    out[запись.имя] = запись.encode(v); ошибка → Encode(имя, причина)
  для каждого (имя, сырое) в metadata.сырые:
    если имя ∉ out → out[имя] = сырое      # неизвестные и неразобранные сохраняются
  вернуть out

resolve<T>(metadata, registry):
  если есть типизированное T → вернуть клон
  имя = registry.имя_типа(T); нет → вернуть None
  сырое = metadata.сырые[имя]; нет → вернуть None
  разобрать сырое как T; ошибка → Unparsable(имя, T, причина)
  вернуть значение                            # кэширования нет: Metadata не изменяется
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| `insert` того же типа дважды | Второе значение заменяет первое (критерий заявки №2) |
| Типизированное и сырое значение под одним именем | При кодировании побеждает типизированное |
| `resolve` типа, которого нет в реестре, при наличии сырых значений | `None`: без имени нечего разбирать |
| Пустые метаданные | `encode` возвращает пустой объект |
| `decode` объекта с именем `trace_parent` | Сохраняется в сырой части, как любое другое |
| `advance` из терминального состояния | `InvalidTransition`, состояние то же |
| `advance` в то же состояние | `InvalidTransition`: пар «X → X» в таблице нет |
