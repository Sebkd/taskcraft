## Context

Процесс помечает себя живым в `taskcraft_processes`: при старте это делает `claim_process_id` (`crates/taskcraft-postgres/src/store.rs:470`), потом каждый интервал — `upkeep_once`. Отметку никто не снимает. Фоновые задачи (обслуживание и слушатель `LISTEN`) останавливаются в `Drop for Shared`, то есть когда удалён последний клон хранилища и последний источник.

Отсюда два следствия:
1. Новый запуск с тем же идентификатором в течение двух интервалов «жив» (по умолчанию 20 с) получает `ProcessIdTaken` — проба это подтвердила.
2. Задачи, которые остановка монитора прервала, остаются за процессом в нетерминальном состоянии. Без аренды их получит только следующий запуск этого процесса, с арендой — любой процесс, но после истечения аренды.

Готовые части: `return_tasks` (`store.rs:513`) возвращает нетерминальные задачи владельца в «В очереди» с сохранённым счётом попыток; `alive` (`store.rs:492`) берёт advisory-блокировку идентификатора; `release_process` делает то же самое для чужого, выведенного из работы процесса и пишет журнал `recovery/released`.

## Goals / Non-Goals

**Goals**
- `PgStore::close().await` — штатное завершение процесса: его задачи сразу доступны другим, а его идентификатор свободен для перезапуска.

**Non-Goals**
- Закрытие в `Drop`: асинхронную работу с базой из `Drop` надёжно не сделать.
- Закрытие пула: пул может принадлежать приложению (`with_pool`).
- Защита от вызова до остановки монитора (см. D-3).

## Decisions

### D-1. Что делает `close`

`pub async fn close(&self) -> Result<u64, PgStoreError>`; возвращает число возвращённых задач.

1. Останавливает обслуживание и слушатель уведомлений (`abort` фоновых задач из `Shared::upkeep`). Без этого отметка «жив» вернулась бы на следующем такте.
2. Одной транзакцией под блокировкой идентификатора (как в `alive`):
   - `return_tasks(свой идентификатор)`;
   - `DELETE FROM taskcraft_processes WHERE id = $1`. После удаления отметки нет вовсе, и `claim_process_id` у нового запуска проходит.
3. Сообщает о работе в очередях, куда вернулись задачи (`announce`), — как `release_process`.
4. Пишет журнал INFO `recovery/released`, `tasks released: owner={}, count={}`, — как `release_process`, с собственным идентификатором.

Шаги 2–4 — общая часть с `release_process`. Выношу её в функцию `release(shared, owner, tx)`.

### D-2. Повторный вызов

Повторный `close` безопасен: фоновых задач уже нет, задач процесса нет, удалять отметку нечего — возвращает 0 и пишет журнал с `count=0`. Отдельный флаг «закрыто» не заводится.

### D-3. Порядок остановки — документация, а не проверка

`close` вызывают после того, как `Monitor::run` вернулся. Если вызвать раньше, работающие задачи уйдут в очередь, пока процесс их исполняет, и другой процесс запустит их второй раз. Это та же опасность, что у `release_process` для живого процесса. Запрещать хранилищу работу после `close` (новая ошибка источника) не стал: заявка совместимая, а сценарий — явная ошибка вызова. Предупреждение — в документации метода и в README.

### D-4. Примеры

Затронуты два примера:
- `durable-store`: финальная остановка — `stop.cancel(); running.await??; store.close().await?;`. Шаг «процесс падает» остаётся без `close`, это и есть авария.
- `leases-failover`: процесс B закрывается штатно после `running_b`.

### D-5. Тесты

В `crates/taskcraft-postgres/tests/store.rs`:
1. **`closed_process_id_restarts_at_once`**: хранилище закрыто → хранилище с тем же идентификатором подключается сразу (без `close` — `ProcessIdTaken`, проверено пробой).
2. **`close_releases_unfinished_tasks`**: хранилище без аренды. Через `TaskStore` две задачи взяты и переведены в «В работе», затем `close()` → 2. Другой процесс сразу берёт обе, счёт попыток сохранён. Журнал `recovery/released` с `count=2` (есть хелпер `Logs`).
3. **Повторный `close`** → 0, без ошибок. Проверяется в тесте 1.

### D-6. Версия

Новый метод — совместимое дополнение, `semver-checks` его пропустит. Выпуск 0.3.1.

## Risks / Trade-offs

- `close` до остановки монитора — двойной запуск задачи (D-3). Это видно в документации, пример показывает правильный порядок.
- Аварийная остановка `close` не вызывает. Тогда работает как сейчас: рестарт с тем же идентификатором или аренда.
