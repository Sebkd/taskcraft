## Context

Воркер (`worker-loop-and-supervision`) уже работает. Слоты конкурентности в нём — `tokio::sync::Semaphore` очереди, и воркер занимает слот **до** опроса источника (`run_worker` в `worker.rs`). Это «ждать» с нулевым лимитом ожидания: при занятых слотах источник не опрашивается. Пулов ресурсов нет.

Заявка добавляет три вещи:

- выбор поведения при переполнении: «ждать» с лимитом ожидания или «отказать» с хуком (правило 2.3.7, сценарии 2.2.1 и 2.2.2);
- именованные пулы ресурсов монитора, которые задача занимает перед попыткой (правило 2.3.8);
- освобождение слотов и разрешений при любом исходе (инвариант 1.3.6).

Критерии: спецификация №13, №14, №15, №16, №40, №41; критерий заявки №1 — регистрация очереди с неизвестным пулом.

Границы:
- **Слот во время паузы повтора (2.3.5) — в `retry-policy`.**
- **Задачи из хука восстановления и аренды, не отвергаемые никогда (2.3.7 п. 6), — в `ownership-and-recovery` и `durable-task-store`.** Здесь в них нет нужды: таких задач ещё нет.
- **Отмена по запросу и таймаут попытки — в `task-registry` и `ownership-and-recovery`.** Критерий №15 проверяется для исходов, существующих сейчас: успех, ошибка, паника, «повторить», остановка с прерыванием.

## Goals / Non-Goals

**Goals:**

- `OverflowPolicy` в настройках очереди: «ждать» с лимитом ожидания (по умолчанию — равен лимиту конкурентности, 2.8) или «отказать» с хуком отказа.
- Ожидание слота в порядке приёма, прерываемое остановкой; ограничение на число ожидающих.
- Пулы ресурсов: объявление в мониторе, требование пулов в очереди, проверка при регистрации, захват в порядке возрастания имён, освобождение при любом исходе.
- Журнал WARN `task/rejected` по 2.9.

**Non-Goals:** см. «Границы».

## Decisions

### `OverflowPolicy` и хук отказа в построителе очереди

**Решение**:
- `QueueBuilder::wait_limit(n)` — «ждать» с лимитом ожидания n (n ≥ 0). По умолчанию политика «ждать» с лимитом, равным лимиту конкурентности.
- `QueueBuilder::reject_with(hook)` — «отказать». Хук `Fn(Task<Args>) + Send + Sync + 'static` получает отвергнутую задачу во владение: формирует ответ отправителю и может отправить его в отдельной задаче.
- Внутри — `OverflowPolicy::Wait { limit }` или `OverflowPolicy::Reject(hook)`.

**Обоснование**:
- 2.8: политика «ждать» по умолчанию, лимит ожидания по умолчанию равен лимиту конкурентности.
- 2.10: «отказать» требует хук. Политика без хука здесь невыразима по построению: ошибка конфигурации невозможна.
- Задача отдаётся во владение: хуку нужны идентификатор и аргументы, чтобы ответить отправителю, а воркеру задача после отказа не нужна.

**Альтернативы**:
- Асинхронный хук — отклонено: асинхронный хук остановил бы цикл приёма до своего завершения, а отказ должен быть мгновенным (инвариант 1.3.17). Асинхронный ответ хук отправляет сам через `tokio::spawn`.

### Ожидание слота — две очереди разрешений

**Решение**: у воркера два семафора:
- `slots` — лимит конкурентности;
- `waiting` — лимит ожидания.

Цикл приёма при политике «ждать»:

1. Перед опросом `select!` с приоритетом остановки:
   - **свободный слот** — сразу с разрешением слота;
   - **место в ожидании** — с разрешением ожидания;
   - **остановка** — «Дренаж».

   При лимите ожидания 0 место в ожидании не освобождается никогда, и поведение совпадает с прежним.
2. Ответ «пусто», «закрыт» или ошибка → разрешение отпускается.
3. Задача принята:
   - есть разрешение слота → исполнение сразу;
   - есть разрешение ожидания → сначала `try_acquire` слота (вдруг уже освободился). Не вышло — задача уходит в `JoinSet` с разрешением ожидания и ждёт слот там: `acquire_owned` в `select!` с остановкой. Получив слот, отпускает место в ожидании.

При политике «отказать»:

1. Опрос без ожидания.
2. После приёма — `try_acquire` слота.
3. Не вышло:
   - хук отказа (под `catch_unwind`, как dead-letter);
   - ack сообщения;
   - журнал WARN `task/rejected`;
   - следующий опрос без паузы (сценарий 2.2.1, инвариант 1.3.17).

Ожидающая задача отменяется **сразу** по сигналу остановки: «Принята» → «Отменена» по 2.3.14 п. 4; ack «после завершения» не выполняется (2.2.7). Это входит в счётчик `cancelled` итога остановки.

**Обоснование**:
- 2.3.7 пп. 2–5 и 2.2.2.
- `tokio::sync::Semaphore` честный (FIFO), поэтому слоты выдаются ожидающим в порядке приёма.
- Семафор ожидания делает «воркер не опрашивает источник, пока места в ожидании нет» естественным: ждать нечего, кроме места.
- Остановка видна в каждом ожидании: инварианты 1.3.7, 1.3.17, критерии №40, №41.

**Альтернативы**:
- Счётчик ожидающих с `Notify` — отклонено: два семафора дают то же без ручной синхронизации и без потерянных пробуждений.

### Пулы ресурсов — в мониторе, требования — в очереди

**Решение**:
- `Monitor::pool(name, size) -> Result<Monitor, ConfigError>` — пул с именем и размером ≥ 1. Повтор имени — ошибка.
- `QueueBuilder::pool(name, permits)` — очередь занимает `permits` разрешений пула на каждую попытку. Набор хранится в `BTreeMap`, то есть упорядочен по имени.
- `Monitor::register` проверяет пулы очереди:
  - пула нет → `ConfigError::UnknownPool { name }` («unknown pool»);
  - разрешений больше размера → `ConfigError::PermitsExceedPool { name }` («permits exceed pool size»);
  - разрешений 0 → та же ошибка с текстом «permits must be at least 1».

  Затем в воркер передаётся список `(имя, Arc<Semaphore>, разрешения)` в порядке имён.
- `execute` перед попыткой занимает разрешения всех пулов по порядку: `acquire_many_owned` в `select!` с остановкой.
  - Остановка во время ожидания → «Отменена» (задача ещё «Принята»); уже занятые разрешения освобождаются вместе с разрешениями-значениями.
  - Разрешения живут до конца попытки и освобождаются при любом исходе, включая принудительное прерывание (`OwnedSemaphorePermit` отпускается при уничтожении future).

**Обоснование**: 2.3.8 пп. 1–6. Единый порядок захвата исключает взаимную блокировку (критерий №16). Пул — сущность монитора, общая для всех очередей.

**Альтернативы**:
- Пулы как отдельный объект, передаваемый очередям вручную — отклонено: проверка «пул существует» при регистрации требует, чтобы им владел монитор.

### Ошибки конфигурации

**Решение**: новые варианты `ConfigError`:
- `UnknownPool { name }` — «unknown pool: {name}»;
- `PermitsExceedPool { name }` — «permits exceed pool size: {name}»;
- `InvalidPool { name, reason }` — размер 0, повтор имени, 0 разрешений.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Хук отказа долгий и синхронный | Цикл приёма стоит, пока хук работает | Документация: хук формирует ответ и отправляет его асинхронно сам |
| Ожидающие задачи занимают место в `JoinSet` | Память на ожидающих | Ограничено лимитом ожидания |
| Разрешения пула занимаются после слота | Задача держит слот, ожидая пул | Совпадает с 2.3.7 п. 1: «Принята», получившая слот и ждущая пулов, держит слот |

## Архитектура

### Компонентная диаграмма

```
политика «ждать»:   select { слот | место в ожидании | остановка } ─► опрос ─► задача
                        слот ─► execute ─► пулы (по именам) ─► попытка
                        место в ожидании ─► try слот ─┬─ есть ─► execute
                                                      └─ нет ─► JoinSet: ждать слот (FIFO) | остановка → «Отменена»
политика «отказать»: опрос ─► задача ─► try слот ─┬─ есть ─► execute
                                                  └─ нет ─► хук отказа, ack, WARN task/rejected

Monitor { pools: имя → Semaphore(size) } ── register(queue) ── проверка пулов ─► Vec<(имя, пул, разрешения)>
```

### Новые пакеты/модули

Нет; изменения в `queue.rs`, `worker.rs`, `monitor.rs`, `error.rs`.

## Детали реализации

### Алгоритмы

```
гейт(«ждать»):
  select biased { остановка → дренаж; слот → Gate::Slot(p); место → Gate::Waiting(w) }

приём(задача, гейт):
  Gate::Slot(p)     → spawn execute(p)
  Gate::Waiting(w)  → если try слот → drop(w), spawn execute
                      иначе spawn { select { остановка → «Отменена»; слот → drop(w), execute } }
  «отказать»        → если try слот → spawn execute иначе хук, ack, WARN

execute: для (пул, n) в порядке имён: select { остановка → «Отменена»; acquire_many(n) }
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| Лимит ожидания 0 | Поведение прежнее: опрос только при свободном слоте |
| Хук отказа паникнул | Журнал ERROR `task/reject_failed`, сообщение всё равно подтверждается |
| Ack отказа не удался | Как любая ошибка ack — «Перезапуск» |
| Остановка, задача ждёт слот | «Отменена» сразу, без ack «после завершения» |
| Остановка, задача ждёт пул | То же; слот освобождается |
| Пул меньше разрешений очереди | Ошибка регистрации |
