## Context

`KafkaSource` выдаёт сообщения раздела по порядку, а фиксирует смещения по границе: незавершённая задача держит фиксацию всех следующих (`crates/taskcraft-kafka/src/source.rs`, правило 2.3.9 п. 5). Порядок *обработки* определяет воркер ядра. В документации об этом нет ни слова:
- README пакета, раздел «How it works»;
- документация модуля (`lib.rs`) и `KafkaSource`;
- спецификация 2.6, «Пакет `taskcraft-kafka`».

При разборе выяснилось, что конкурентности 1, которую называет заявка, **недостаточно**:
- по умолчанию задача в паузе повтора освобождает слот (правило 2.3.5, `RetryPolicy::hold_slot = false`), и следующее сообщение раздела исполняется раньше повтора;
- «отложить» у Kafka тоже ждёт в процессе (правило 2.3.6 п. 2, источник без отложенного повтора) через ту же паузу (`worker/execute.rs`, `Next::Pause`), и слот освобождается так же.

Порядок сохраняется, только если слот удерживается: `RetryPolicy { hold_slot: true, .. }`. Задачи, ждущие слота, получают его в порядке приёма (сценарий 2.2.2 п. 2).

## Goals / Non-Goals

**Goals**
- Читатель README и документации знает, при каких настройках обработка идёт строго по порядку раздела, и что происходит в остальных случаях.

**Non-Goals**
- Порядок по ключу при конкурентности больше 1.
- Новые настройки или изменение поведения.

## Decisions

### D-1. Условия строгого порядка (уточнение заявки)

Строгий порядок внутри раздела в одном процессе дают одновременно:
1. конкурентность очереди 1;
2. `RetryPolicy { hold_slot: true, .. }` — слот удерживается в паузе повтора и при «отложить».

Пул ресурсов на порядок не влияет: задача ждёт разрешение, держа слот.

Оговорки, которые тоже войдут в текст:
- Порядок задаёт ещё и доставка «хотя бы раз». После аварии или перебалансировки сообщения от последнего зафиксированного смещения доставляются снова, в том числе уже обработанные. Порядок первой обработки сохраняется, но повторы возможны.
- При ack «после приёма» задачи из хука восстановления исполняются в порядке, который вернул хук.

При конкурентности больше 1 или без `hold_slot` сообщения одного раздела исполняются параллельно и завершаются в любом порядке. Фиксация смещений при этом остаётся верной: граница не пропускает незавершённую задачу.

### D-2. Где писать

- README пакета, раздел «How it works»: новый пункт **Order within a partition**, с примером `.concurrency(1)` и `RetryPolicy { hold_slot: true, ..}`.
- Документация `lib.rs` (страница docs.rs) — тот же пункт кратко.
- Документация `KafkaSource` — одна строка со ссылкой на условия.
- Спецификация 2.6, «Пакет `taskcraft-kafka`»: пункт «Порядок обработки внутри раздела».

### D-3. Тест на «отложить» с удержанием слота

Удержание слота в паузе *повтора* уже проверяют `held_slot_keeps_other_tasks_waiting_through_the_pause` и `released_slot_lets_another_task_run_during_the_pause` в `crates/taskcraft/tests/retry.rs`. Для «отложить» в процессе такой проверки нет, а документация на это опирается.

Хелпер `second_task_start(hold_slot)` получает второй параметр — исход первой попытки: «повторить» или «отложить(60 с)». Добавляются два теста, `held_slot_keeps_other_tasks_waiting_through_a_defer` и `released_slot_lets_another_task_run_during_a_defer`, на виртуальном времени.

Тест порядка с брокером не нужен: источник выдаёт сообщения раздела по порядку (это свойство Kafka), а порядок исполнения — дело ядра, и его покрывают тесты выше.

### D-4. Версия

Документация и тест, код не меняется. Выпуск 0.3.1: README попадёт на crates.io с выпуском.

## Risks / Trade-offs

- `hold_slot` при конкурентности 1 останавливает очередь на время паузы. Это цена порядка, и в README это сказано прямо.
