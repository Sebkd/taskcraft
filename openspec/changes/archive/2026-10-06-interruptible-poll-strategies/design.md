## Context

В ядре уже есть контракт источника с пробуждением (`Source::subscribe`, `WakeSignal`: `mark_seen` перед опросом и `changed` после ответа «пусто»), токен отмены `tokio_util::sync::CancellationToken` и харнесс на виртуальном времени. Воркера ещё нет. Эта заявка даёт ему ответ на вопрос «сколько ждать после ответа „пусто“» и сон, который прерывается остановкой и пробуждением.

Требования:

- **Спецификация 2.3.24.** Стратегии:
  - фиксированный интервал;
  - рост от минимума до максимума с множителем 2 и сбросом при первой задаче;
  - ожидание пробуждения от источника;
  - композиция «первое из нескольких».

  Сон кончается при первом из трёх событий: время истекло, источник разбудил, пришёл сигнал остановки. Все таймеры — на tokio.
- **Спецификация 2.8.** По умолчанию — «пробуждение или рост 100 мс…30 с, множитель 2».
- **Критерий спецификации №20.** Воркер в «Ожидании» со сном 30 с, подан сигнал остановки — немедленно в «Дренаж». Здесь закрывается часть про сон; переход состояния выполнит воркер.
- **Критерии заявки.** №1 — последовательность снов 100, 200, 400, 800, 1600 мс и сброс. №2 — пробуждение посреди сна.

Дефекты apalis, которые закрывает заявка:
- A-4: остановка досыпает бэкофф до минуты;
- A-6: таймеры мимо исполнителя, время в тестах не виртуализуется.

## Goals / Non-Goals

**Goals:**

- `PollStrategy` — стратегия как данные, четыре вида, умолчание по 2.8.
- `Poller` — состояние стратегии одного воркера: длительность следующего сна, сброс после задачи.
- `Poller::wait` — сон до первого из событий «время / пробуждение / остановка», с результатом `Wakeup`.

**Non-Goals:**

- Сам цикл воркера и переходы 2.4.2 — `worker-loop-and-supervision`.
- Чтение стратегии из конфигурационного файла — вместе с конфигурацией очереди: сериализация длительностей в удобном виде («100ms») выбирается там.
- Пауза повтора и задержка перезапуска — свои правила (2.3.4, 2.3.12). Прерываемость остановкой у них реализуется тем же `tokio::select!` по токену.

## Decisions

### `PollStrategy` — перечисление, композиция — список

**Решение**:

```rust
pub enum PollStrategy {
    Interval(Duration),
    Backoff { min: Duration, max: Duration },
    Wake,
    FirstOf(Vec<PollStrategy>),
}
```

- Множитель роста — 2, как в 2.3.24.
- `Default` — `FirstOf([Wake, Backoff { 100 мс, 30 с }])`.
- Проверка `validate()`:
  - `Interval` > 0;
  - у `Backoff` `0 < min ≤ max`;
  - `FirstOf` не пуст.

  Нарушение — `ConfigError::InvalidPollStrategy { reason }`; текст из 2.10 («duration must be positive», «base delay exceeds max delay»). Вложенные `FirstOf` допустимы и разворачиваются.

**Обоснование**: 2.3.24 п. 1 перечисляет ровно эти виды. Данные, а не трейт: стратегия — часть конфигурации очереди (2.8), её строят, сравнивают и печатают.

**Альтернативы**:
- Трейт стратегии с пользовательскими реализациями — отклонено: спецификация задаёт закрытый набор, а расширяемость здесь не требуется.

### `Poller` — развёрнутое состояние стратегии

**Решение**: `Poller::new(&PollStrategy)` разворачивает дерево в плоское состояние:
- список таймеров: `Interval(d)` или `Backoff { min, max, next }`;
- флаг `wake` — есть ли среди элементов `Wake`.

Методы:

| Метод | Поведение |
|-------|-----------|
| `next_sleep() -> Option<Duration>` | Минимум текущих значений таймеров; у каждого `Backoff` после этого `next = min(next × 2, max)`. `None` — таймеров нет (чистое ожидание пробуждения) |
| `reset()` | Вызывается после выданной задачи: все `Backoff` возвращаются к `min` (сброс при первой задаче) |
| `wants_wake()` | Есть ли `Wake` |

**Обоснование**: критерий заявки №1. У каждого `Backoff` композиции своё состояние; плоский список проще дерева и даёт «первое из нескольких» как минимум таймеров.

### `Poller::wait` — сон до первого события

**Решение**:

```rust
pub async fn wait(&mut self, wake: Option<&mut WakeSignal>, stop: &CancellationToken) -> Wakeup
```

`Wakeup` — `Elapsed`, `Woken`, `Stopped`.

1. Остановка уже подана → сразу `Stopped`.
2. Длительность — `next_sleep()`.
3. Пробуждение используется, если `wants_wake()` и сигнал передан.
4. Нет ни таймера, ни используемого пробуждения (`Wake` у источника без сигнала) → **запасной рост** 100 мс…30 с, а не вечный сон. Запасное состояние хранится в `Poller` и тоже сбрасывается `reset()`.
5. `tokio::select!` с приоритетом `biased` в порядке: остановка, пробуждение, таймер.
   - Пробуждение, вернувшее `false` (источника больше нет), считается `Woken`: следующий опрос сам покажет, что с источником.
6. Таймер — `tokio::time::sleep`: в тестах время виртуальное (2.3.24 п. 4).

Протокол для воркера:
- `mark_seen()` на сигнале **перед** опросом;
- после ответа «пусто» — `wait`;
- после выданной задачи — `reset()`.

**Обоснование**:
- 2.3.24 п. 3 и критерии №20, заявки №2.
- `biased` с остановкой первой гарантирует, что одновременные «остановка» и «пробуждение» дадут `Stopped`.
- Запасной рост закрывает ловушку «`Wake` у источника без пробуждения» — иначе воркер уснул бы навсегда.

**Альтернативы**:
- Возвращать из `Poller` только длительность, а `select!` писать в воркере — отклонено: тот же код понадобится воркеру, тестам харнесса и, возможно, источникам. В одном месте его проще проверить.
- Вечный сон при `Wake` без сигнала — отклонено: воркер, который не опрашивает источник, неотличим от зависшего.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Отложенная задача in-memory наступает без пробуждения | Воркер узнает о ней на следующем тике таймера | Умолчание содержит рост до 30 с; задокументировано |
| `Wake` с источником без сигнала | Неожиданно частые опросы вместо ожидания | Запасной рост ограничен 30 с; поведение описано в документации `PollStrategy::Wake` |
| `Duration × 2` переполняется | Паника | Умножение через `saturating_mul`, затем `min(max)` |

## Архитектура

### Компонентная диаграмма

```
воркер (позже):
  wake.mark_seen() → source.poll() ─┬─ Task  → poller.reset() → исполнение
                                    └─ Empty → poller.wait(wake, stop) ─┬─ Elapsed → опрос
```

## Детали реализации

### Алгоритмы

```
next_sleep:
  если таймеров нет → None
  d = min(значение каждого таймера)
  для каждого Backoff: next = min(next × 2, max)
  вернуть d

wait(wake, stop):
  если stop отменён → Stopped
  d = next_sleep()
  ждать первого: stop → Stopped; (wake, если wants_wake и сигнал есть) → Woken;
                 таймер d (или запасной рост, если ждать больше нечего) → Elapsed
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| `Backoff { min = max }` | Постоянный интервал |
| Остановка и пробуждение одновременно | `Stopped` (приоритет остановки) |
| Сигнал пробуждения «источник уничтожен» | `Woken`, следующий опрос покажет состояние источника |
| `FirstOf([Wake])` у источника без сигнала | Запасной рост 100 мс…30 с |
| Пустой `FirstOf` | Ошибка `validate` |

## Тестирование

### Unit-тесты

| Что тестируем | Сценарий |
|---------------|----------|
| `Poller::next_sleep` на росте 100 мс…30 с | 100, 200, 400, 800, 1600; после `reset` — снова 100 (критерий заявки №1); потолок 30 с не превышается |
| `FirstOf([Interval 1 с, Backoff 100 мс…30 с])` | Сон — минимум, рост продолжается внутри |
| `validate` | Нулевой интервал, `min > max`, пустой `FirstOf` — ошибки |
| `wait`: время | Виртуальное время продвигается ровно на длительность сна, результат `Elapsed` |
| `wait`: пробуждение посреди сна | Постановка в `InMemorySource` во время 30-секундного сна → `Woken` раньше 30 с (критерий заявки №2) |
| `wait`: остановка посреди сна 30 с | `Stopped` без продвижения часов на 30 с (спецификация №20, часть сна) |
| `wait`: `Wake` без сигнала | Запасной рост: `Elapsed` через 100 мс |
| Одновременные остановка и пробуждение | `Stopped` |
