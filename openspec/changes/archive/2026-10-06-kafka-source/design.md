## Context

Ядро уже содержит контракт источника (`Source`, `Polled`, `Capabilities` с `AckPointSupport::QueueOnly`), учёт границы фиксации (`OffsetTracker`), кодеки, реестр метаданных и воркер с перезапуском после ошибок источника. Журнального источника нет.

Требования:

- **2.6 «Пакет taskcraft-kafka».** Потребитель топика в группе; автофиксация выключена всегда; ack — фиксация смещения; постановки и отложенного повтора нет; идентификатор — функцией, по умолчанию ключ, без ключа — генерируется и WARN один раз; метаданные из заголовков; недоступный брокер — ошибка источника; разделы раздаёт Kafka.
- **2.8 «Источник Kafka»** — параметры: брокеры, топик, группа, функция идентификатора, дополнительные свойства.
- **2.3.9 п. 5** — граница фиксации.
- **2.12** — заголовки под зарегистрированными именами.
- **Критерии:** спецификация №23; критерии заявки №1–№5.

Ядро не должно зависеть от Kafka (инвариант 1.3.14, критерий №33).

## Goals / Non-Goals

**Goals:**

- Пакет `crates/taskcraft-kafka`: `KafkaSource`, `KafkaSourceBuilder`, `KafkaMessage`, `KafkaReceipt`, `KafkaJsonCodec`, `KafkaSourceError`.
- Интеграционные тесты на настоящем брокере в отдельном job CI.

**Non-Goals:**

- Отложенный повтор — Kafka его не поддерживает (правило 2.3.6).
- Публикация пакета на crates.io — вместе с `taskcraft` 0.1.0.

## Decisions

### Клиент — `rdkafka`

**Решение**: `rdkafka` 0.39, возможности `libz` и `tokio`, без возможностей по умолчанию. librdkafka собирается из исходников (`configure` + `make`), cmake не нужен.

**Обоснование**: группы потребителей, ребаланс и ручная фиксация есть и проверены в эксплуатации. Решение согласовано с владельцем проекта.

**Альтернативы**:
- Клиенты на чистом Rust — отклонено: нет групп потребителей и ребаланса, раздачу разделов (критерий заявки №5) пришлось бы писать самим.

### Учёт фиксаций с номером назначения раздела

**Решение**: `Commits` — `HashMap<partition, Partition { assignment, OffsetTracker, committed }>`.

- Квитанция `KafkaReceipt { partition, offset, assignment }`.
- Раздел, впервые встреченный опросом, получает новый номер назначения.
- Ребаланс с отзывом (`ConsumerContext::pre_rebalance`) удаляет разделы.
- Ack из прежнего назначения ничего не фиксирует: та же выдача достанется другому потребителю группы.
- `acked` возвращает следующее смещение для чтения (`commit_point + 1`), только когда точка фиксации сдвинулась.

**Обоснование**: 2.3.9 п. 5. Номер назначения защищает от ack старой выдачи после повторного назначения того же раздела, когда смещения совпадают.

### Фиксация — асинхронная, сразу при сдвиге границы

**Решение**: `ack` → `Commits::acked` → `consumer.commit(offsets, CommitMode::Async)`. Ошибка постановки фиксации → ошибка источника → обработчик 2.1.2.6.

**Обоснование**: синхронная фиксация блокировала бы поток исполнителя на круг до брокера. Порядок фиксаций одного потребителя librdkafka сохраняет.

### Длинный опрос и пробуждение

**Решение**: `poll` ждёт сообщение до `max_wait` (по умолчанию 1 с). Не дождался — будит собственный `WakeSignal` и отвечает «пусто». Стратегия опроса по умолчанию («пробуждение или рост») тогда сразу опрашивает снова.

**Обоснование**: без этого после серии пустых ответов пауза выросла бы до 30 с и задержала бы первую задачу. `recv` безопасен к отмене, поэтому сигнал остановки прерывает ожидание без потери сообщения.

### Идентификатор и метаданные

**Решение**:
- `KafkaSourceBuilder::task_id(f)`: `f(&KafkaMessage) -> Option<TaskId>`, по умолчанию — ключ как текст. `None` → остаётся сгенерированный идентификатор; первое такое сообщение источника → WARN `source/key_missing`.
- `KafkaJsonCodec<Args>`: тело — JSON аргументов. Заголовки с именем из реестра (`MetadataRegistry::is_registered`, новый метод ядра; включает `trace_parent`) — сырые метаданные. Значение заголовка — JSON; не JSON, но UTF-8 — строка JSON. Нет тела или тело не разбирается → `CodecError::Decode`, отравленное сообщение (2.2.4). `encode` — ошибка: источник задачи не принимает.

**Обоснование**: производители пишут в топик аргументы, а не конверт `JsonCodec`. Своё тело — свой кодек: `Codec<Args, KafkaMessage>` реализуется потребителем.

### Журнал WARN `key_missing` с топиком вместо имени очереди

**Решение**: сообщение `message without key, task id generated: topic={}`.

**Обоснование**: источник не знает имени очереди, которой он отдан. Топик однозначно указывает на очередь первого потребителя. Строку таблицы 2.9 обновить при применении.

### Недоступный брокер

**Решение**: ошибки чтения из `recv` → `KafkaSourceError::Client`. Ошибки клиента `AllBrokersDown` и `Fatal` из `ClientContext::error` запоминаются и отдаются следующим опросом как `KafkaSourceError::Broker`. Остальные ошибки клиента — WARN `source/client_error`.

**Обоснование**: критерий заявки №4 — ошибка источника и перезапуск по 2.3.12. Фиксаций без завершённых задач нет.

### Свойства клиента

**Решение**: `bootstrap.servers`, `group.id` и `auto.offset.reset=earliest` по умолчанию. Затем свойства потребителя. Затем принудительно `enable.auto.commit=false` и `enable.auto.offset.store=false`.

**Обоснование**: критерий заявки №1. `earliest` — новая группа не пропускает задачи, записанные до её первого запуска; потребитель может задать своё.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Нативная сборка librdkafka | Нужны C-компилятор и make; сборка дольше | Только в `taskcraft-kafka`; ядро не затронуто (критерий №33) |
| Задача отозванного раздела дорабатывает у старого владельца | Повторное исполнение у нового | At-least-once по спецификации; идемпотентность обработчика |
| `taskcraft` на crates.io — заглушка 0.0.0 | `cargo publish --dry-run` пакета Kafka не собирается | `publish = false` до 0.1.0; CI пропускает такие пакеты |
