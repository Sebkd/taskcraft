## Context

Публичный интерфейс первой версии устоялся: ядро, `taskcraft-kafka`, `taskcraft-postgres`, запускаемое, наблюдатель. Сценарии первого потребителя проверены тестами (`consumer-scenarios`). Примеров нет: документация — rustdoc и спецификация.

Нужно 15 примеров (E-1…E-15), README каталога со ссылками на разделы спецификации, docker compose для Kafka и PostgreSQL и проверка в CI.

---

## Goals / Non-Goals

**Goals:**

- E-1…E-15, README каталога, docker compose, CI.

**Non-Goals:**

- Новое поведение библиотеки.
- Вариант E-15 с общей реализацией за возможностью `statecraft`: заявка `terminal-state-outcome` в statecraft-fsm не влита. Пример показывает адаптер «в нынешнем виде»; README отмечает, что второй вариант появится вместе с возможностью.

## Decisions

### Где лежат примеры

**Решение**:

| Примеры | Место | Почему |
|---------|-------|--------|
| E-1…E-10, E-15 | `crates/taskcraft/examples/` | Нужно только ядро; E-10 — с возможностью `metrics`, E-15 — со statecraft-fsm (уже dev-dependency) |
| E-12 | `crates/taskcraft-kafka/examples/` | Нужен пакет Kafka |
| E-13, E-14 | `crates/taskcraft-postgres/examples/` | Нужен пакет хранилища |
| E-11 | `examples/axum-service/` — отдельный крейт вне workspace, как `examples/axum_fsm` в statecraft | axum и hyper не попадают в `Cargo.lock` workspace и в cargo-vet/cargo-deny библиотеки |

В корневом `examples/` лежат также `README.md` каталога и `docker-compose.yml`.

**Обоснование**: примеры собираются как dev-target своего пакета и видят его dev-dependencies. Тяжёлые веб-зависимости остаются вне цепочки поставки библиотеки.

### Примеры проверяют себя сами

**Решение**:
- Каждый пример — `main`, который печатает ход работы и в конце итог. Ожидания проверяются внутри примера; при расхождении он завершается с ошибкой (`Result` из `main`), а не печатает неверный итог.
- Долгие примеры (E-3, E-4, E-15 и др.) работают на виртуальном времени: `#[tokio::main(flavor = "current_thread", start_paused = true)]`. Часы шагают сами, многочасовые задачи проходят за миллисекунды; в выводе — виртуальное время.
- Рабочий код примеров без `unwrap`/`expect`: ошибки идут через `?`. Это показ правильного стиля, а не только требование 1.3.19.

**Обоснование**: критерий заявки №2 — «завершается сам и печатает ожидаемый итог». Проверка внутри примера надёжнее, чем сравнение текста вывода в CI.

### CI: примеры собираются, но не запускаются

**Решение** (согласовано с владельцем проекта):
- Примеры workspace собирает и проверяет существующий шаг `cargo clippy --workspace --all-targets --all-features` (критерий заявки №1); отдельного шага не нужно.
- E-11 вне workspace: новый шаг `cargo clippy --manifest-path examples/axum-service/Cargo.toml -- -D warnings`.
- Примеры в CI не запускаются.

### Как примеры остаются актуальными

**Решение**:

| Что проверяет | Как |
|---------------|-----|
| API | Компилятор и линтер в CI: пример, отставший от API, не собирается |
| Поведение | Правило процесса заявок: в design.md каждой заявки — пункт «Затронутые примеры» (по таблице README каталога, которая связывает примеры с разделами спецификации); в tasks.md — обновить их и прогнать вручную |
| Итог | Самопроверка внутри примера: при ручном запуске расхождение — ошибка, а не тихо неверный вывод |

### E-6 `graceful-shutdown` — сигнал ОС

**Решение**: `tokio::signal::ctrl_c()` в `select!` с демонстрационным таймером. В CI и без нажатия Ctrl-C пример подаёт сигнал остановки сам по таймеру и печатает итог остановки.

### E-9 `custom-runnable` — не автомат

**Решение**: вычисление в отдельном потоке ОС (`std::thread`) с флагом мягкой остановки — запускаемое, которое не автомат и не tokio-задача.

**Альтернативы**:
- Дочерний процесс ОС — отклонено: мягкая остановка требует сигналов, а `tokio::process` даёт только kill; переносимость хуже.

### E-10 `observability` — Prometheus без HTTP-сервера

**Решение**: dev-dependency `metrics-exporter-prometheus` без возможностей по умолчанию. Пример ставит рекордер, исполняет задачи и печатает текст экспозиции (`render()`), плюс сводку своего наблюдателя. Подписчик — `tracing-subscriber` с `EnvFilter` (`RUST_LOG=taskcraft=debug`, критерий заявки №6).

### E-15 `fsm-pipeline`

**Решение**: автомат «подготовка → копирование частей → упаковка → уведомление → готово».
- Копирование занимает «слот копирования» из пула.
- Уведомление ждёт подтверждения получателя до 6 часов (виртуальное время); подтверждение приходит событием в идущий автомат.
- Записи потребителя — карта «задание → шаг».

Пример проигрывает подряд, с печатью каждого шага:
1. Обычное задание до «готово».
2. Отмена посреди копирования: мягкая остановка, слот освобождён (критерий заявки №4).
3. Паника шага: исход «паника», другие задания живут.
4. Сбой процесса посреди уведомления: хук восстановления, продолжение с сохранённого шага (критерий заявки №5).

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Крейт E-11 вне workspace | Его зависимости не проходят cargo-vet/cargo-deny | Это пример, не библиотека; проверяется отдельным шагом clippy |
| Новые dev-dependencies (`metrics-exporter-prometheus`, `tracing-subscriber` с `env-filter`) | Больше исключений cargo-vet | Только dev; ядро не затронуто (критерий №33) |
| Виртуальное время в примерах | Пользователь может принять его за реальное | Каждый долгий пример печатает, что время виртуальное, и почему |
