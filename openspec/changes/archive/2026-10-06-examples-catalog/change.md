## 1. Предложение

### Цель изменения

Дать пользователю исполняемую документацию: каталог `examples/` от минимальной очереди до тяжёлого случая с автоматом statecraft-fsm. У apalis каталог из 17 примеров — сильная сторона формы, его стоит повторить. Здесь каждый пример ещё и проверяется в CI, поэтому он не устаревает.

Заявка последняя: примеры опираются на стабильный публичный интерфейс. Сценарии первого потребителя как проверка требований остаются в `consumer-scenarios`; здесь цель другая — показать, как пользоваться библиотекой.

### Инициатор

Разработка первой версии taskcraft (ветка `taskcraft/sebkd-1`). Требования первого потребителя — спецификация, раздел 1.1.

### Затронутые компоненты

- [x] Каталог `examples/` пакета `taskcraft` и примеры пакетов `taskcraft-kafka` и хранилища
- [x] Отдельный крейт примера с axum
- [x] docker compose для примеров с Kafka и PostgreSQL
- [x] CI: сборка и линтер всех примеров; примеры в CI не запускаются

### Приоритет

средний

Да: новая функциональность, публичных версий библиотеки ещё нет.

### Объём реализации

Спецификация 0.1 уже описывает целевое поведение (раздел 1.1, «Статус реализации»). Эта заявка поведение не меняет, а реализует перечисленные разделы. Поэтому разделы 2–15 ниже содержат только уточнения спецификации; где их нет — «Нет изменений.».

**Реализует:**

- Документация: примеры использования разделов 2.1.1, 2.3, 2.5, 2.6, 4.4 спецификации
- E-1 `hello` — минимальная in-memory очередь
- E-2 `outcomes` — успех, повторить, прервать, отложить, паника
- E-3 `long-tasks-reject` — многочасовые задачи, политика «отказать», прерываемая пауза
- E-4 `resource-pools` — пулы, статус и отмена по id
- E-5 `idempotent-push` — повторная постановка
- E-6 `graceful-shutdown` — сигнал ОС, таймаут, итог остановки
- E-7 `metadata` — типы метаданных двух сценариев, реестр
- E-8 `custom-source` — свой источник на контракте
- E-9 `custom-runnable` — своё запускаемое
- E-10 `observability` — подписчик tracing, экспортер Prometheus, свой наблюдатель
- E-11 `axum-service` — постановка, статус и отмена через HTTP
- E-12 `kafka-consumer` — источник Kafka, хук восстановления, два процесса
- E-13 `durable-store` — хранилище без аренды, рестарт
- E-14 `leases-failover` — аренда и подхват задачи
- E-15 `fsm-pipeline` — тяжёлый случай: многошаговая выгрузка автоматом statecraft-fsm с пулом, многочасовым ожиданием, отменой как мягкой остановкой, паникой шага и восстановлением после рестарта

**Не входит:**

- Новое поведение библиотеки: примеры только используют реализованное
- Внедрение в сервисы первого потребителя

**Зависит от заявок:** `consumer-scenarios`, `durable-task-store`

## 16. Рекомендации к критериям приёмки

Критериев спецификации, закрываемых только этой заявкой, нет. Критерии заявки:

| # | КОГДА | ТОГДА |
|---|-------|-------|
| 1 | CI собирает каталог | Собираются все 15 примеров, включая требующие возможностей сборки |
| 2 | Пример без внешней инфраструктуры запускают вручную | Завершается сам, сверяет итог и печатает его, при расхождении завершается с ошибкой; время в долгих примерах виртуальное. В CI примеры собираются и проверяются линтером, но не запускаются |
| 3 | Пользователь запускает E-12…E-14 по README с docker compose | Пример доходит до описанного итога |
| 4 | E-15: отмена задачи посреди процесса | Автомат получает мягкую остановку, задача «Отменена», слот копирования освобождён |
| 5 | E-15: процесс перезапускается посреди уведомления | Хук восстановления поднимает задачу, автомат продолжает с сохранённого шага и доходит до «готово» |
| 6 | E-10 с `RUST_LOG=taskcraft=debug` | В выводе события приёма, старта и исхода попыток с очередью, идентификатором и номером попытки; без значений аргументов |
| 7 | README каталога | Каждый пример связан с разделами спецификации, которые он показывает |
