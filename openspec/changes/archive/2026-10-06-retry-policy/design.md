## Context

Сейчас воркер (`execute` в `worker.rs`) делает ровно одну попытку. «Повторить» сразу даёт «Ошибка» с причиной «попытки исчерпаны». «Отложить» передаётся источнику, если тот умеет; если не умеет или отказал, тоже даёт «Ошибка».

Слот и разрешения пулов задача держит до конца попытки:
- слот — `Slot::Held` или ожидание `Slot::Wait`;
- пулы — `PoolClaim` в порядке имён.

Счётчики уже есть в модели: `Task::begin_attempt` и `Task::count_retry`.

Требования:

- **2.3.3.** Номер попытки растёт на каждый запуск. Лимит M ограничивает только исходы «повторить»; «отложить» его не расходует. Счёт сквозной.
- **2.3.4.** `пауза(k) = min(база × множитель^(k−1), максимум)` и разброс ± r. Задержка от обработчика берётся вместо формулы: ограничена максимумом, без разброса.
- **2.3.5.** Слот во время паузы по умолчанию освобождается; настройка «удерживать слот». Пулы освобождаются всегда.
- **2.3.6.** «Отложить» без поддержки источника или при его отказе — ожидание в процессе с той же задержкой, без лимита и без максимума паузы.
- **2.8, 2.10.** Параметры и их проверки.
- **Критерии:** спецификация №4, №7, №11, №12, а также части №21 и №39 про паузу повтора, перенесённые из `worker-loop-and-supervision`; критерии заявки №1–№3.

Дефект apalis, который закрывает заявка (A-2): повтор держал слот весь бэкофф, а два механизма считали попытки по-разному.

## Goals / Non-Goals

**Goals:**

- `RetryPolicy` — максимум попыток, база, множитель, максимум, разброс, удержание слота; проверка по 2.10; расчёт паузы.
- Цикл попыток в `execute`: пауза прерывается остановкой; слот в паузе освобождается или удерживается; пулы освобождаются и захватываются заново; деградация «отложить».
- Журнал WARN `task/retry` и DEBUG `task/defer_in_process` по 2.9.
- Сценарий харнесса `cancel_during_retry_pause_stops_work` проходит на настоящем воркере.

**Non-Goals:**

- Таймаут попытки и исход таймаута — `ownership-and-recovery`.
- Отмена по запросу во время паузы — `task-registry` (сейчас паузу прерывает только остановка).

## Decisions

### `RetryPolicy` — открытая структура со значениями по умолчанию из 2.8

**Решение**:

```rust
pub struct RetryPolicy {
    pub max_attempts: u32,   // 1
    pub base: Duration,      // 1 с
    pub factor: f64,         // 2.0
    pub max: Duration,       // 5 мин
    pub jitter: f64,         // 0.1
    pub hold_slot: bool,     // false
}
```

- Методы `validate()` и `pause(retries, requested)`.
- Проверки 2.10, текстом в `ConfigError::InvalidRetryPolicy { reason }`:
  - `max_attempts ≥ 1` — «max attempts must be at least 1»;
  - `factor ≥ 1` и конечен — «backoff factor must be at least 1»;
  - `base ≤ max` — «base delay exceeds max delay»;
  - `0 ≤ jitter ≤ 1` — «jitter must be within 0..1».
- `QueueBuilder::retry_policy(policy)`; `build()` вызывает `validate()`.

**Обоснование**: параметры 2.8 один к одному. Открытые поля с `Default` позволяют писать `RetryPolicy { max_attempts: 3, ..Default::default() }`.

**Альтернативы**:
- Отдельный построитель политики — отклонено: у структуры шесть простых полей и одна проверка.

### Расчёт паузы

**Решение**: `pause(k, requested)`:
1. Задержка от обработчика есть → `min(задержка, max)`, разброс не применяется.
2. Иначе `d = min(base × factor^(k−1), max)` в секундах `f64`. Переполнение и бесконечность ограничиваются `max` до перевода в `Duration`.
3. Разброс `r > 0` → `d × u`, где `u` равномерно из `[1 − r, 1 + r]`. Результат в `[0, max]`.

Случайное число — без новой зависимости: 64 бита хэша `std::hash::RandomState` от счётчика вызовов. Это не криптография, только разброс.

**Обоснование**: 2.3.4 пп. 1–5. Критерии заявки №1 (разброс 0 — паузы 1, 2, 4 с) и №2 (10 мин при максимуме 5 мин → 5 мин).

**Альтернативы**:
- Пакет `rand` — отклонено: новая зависимость и запись cargo-vet ради разброса паузы.

### Цикл попыток в `execute`

**Решение**: `execute` становится циклом. Одна итерация:

1. Слот: при первой итерации — из параметра (`Held` или `Wait`); после паузы — удержанный или заново `acquire_owned` в `select!` с остановкой.
2. Пулы по порядку, как сейчас.
3. «Принята» → «В работе», `begin_attempt`, спан, попытка.
4. Признак отмены выставлен остановкой → «Отменена», как сейчас.
5. Исход:

| Исход | Решение |
|-------|---------|
| `Retry { delay }` и `retries < max_attempts − 1` | `count_retry`; пауза `policy.pause(retries, delay)`; WARN `task/retry`; в паузу |
| `Retry`, повторы исчерпаны | «Ошибка», причина `AttemptsExhausted` |
| `Defer` и источник умеет | `source.defer` → «Отложена»; при ошибке — WARN и деградация (2.3.6 п. 4) |
| `Defer` и источник не умеет | Деградация: пауза = задержка исхода, без счётчика повторов, без лимита и без максимума; DEBUG `task/defer_in_process` |
| `Success`, `Abort`, `Panic` | Как сейчас |

6. Пауза:
   - «В работе» → «Ожидает повтора» (2.4.1.5);
   - разрешения пулов отпускаются;
   - слот отпускается, если `hold_slot` выключен (2.3.5);
   - сон `pause` в `select!` с остановкой. Остановка → «Ожидает повтора» → «Отменена» (2.4.1.11), без ack «после завершения» (2.2.7), результат `TaskEnd::CancelledWaiting`, то есть в итоге остановки «отменено».
   - Затем «Ожидает повтора» → «Принята» (2.4.1.10) и следующая итерация.
7. Ack «после завершения» — только после терминального перехода, никогда не во время паузы (критерий №39).

Для повторного захвата слота в `ExecCtx` добавляется `slots: Arc<Semaphore>` и политика повторов очереди.

**Обоснование**:
- Переходы 2.4.1.5, 2.4.1.10, 2.4.1.11 и правила 2.3.3–2.3.6.
- Пауза — внутри задачи исполнения, а не в цикле приёма, поэтому приём не ждёт её (инвариант 1.3.17).
- Повторный захват слота идёт в общую очередь семафора, «на общих основаниях» (2.3.5 п. 2).

**Альтернативы**:
- Возвращать задачу в цикл приёма для повтора — отклонено: цикл приёма решает, что опрашивать, а не когда повторять. Плюс лишняя синхронизация.

### Сценарий харнесса на воркере

**Решение**: `WorkerRunner` в `tests/worker.rs` применяет `max_attempts` и `retry_pause` из `RunnerSetup` как `RetryPolicy { max_attempts, base: retry_pause, factor: 1.0, jitter: 0.0, .. }`. Сценарий `cancel_during_retry_pause_stops_work` добавляется к прогону.

**Обоснование**: настоящий воркер проходит все сценарии харнесса, относящиеся к нему.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Хэш `RandomState` как источник случайности | Разброс не криптостойкий | Нужен только для рассинхронизации повторов |
| Повторный захват слота после паузы | Повтор может ждать слот дольше паузы | Так и задумано 2.3.5 п. 2; удержание слота — настройка |
| «Отложить» в процессе без лимита | Бесконечные отложенные повторы | Так требует 2.3.6 п. 2: «не сейчас», а не «неудача»; остановка прерывает |

## Архитектура

### Компонентная диаграмма

```
execute(task):
  loop {
    слот (первый раз из приёма, далее удержан или заново) ─► пулы ─► «В работе» ─► попытка ─► исход
      Retry, повторы остались ─► count_retry ─► pause(k, delay) ─┐
      Defer, источник не умеет ─► pause = delay ────────────────┤
      Defer, источник умеет ─► source.defer ─► «Отложена»       │
      Success / Abort / Panic / Retry исчерпан ─► итог, ack     │
                                                                ▼
              «Ожидает повтора»: отпустить пулы (и слот, если не hold_slot);
                                 select { остановка → «Отменена», sleep(pause) → «Принята» }
  }
```

### Новые пакеты/модули

| Пакет/Модуль | Назначение |
|--------------|------------|
| `taskcraft::retry` (приватный) | `RetryPolicy`, расчёт паузы, случайная доля |

## Детали реализации

### Алгоритмы

```
pause(k, requested):
  если requested → вернуть min(requested, max)
  d = min(base_s × factor^(k−1), max_s)          # f64, переполнение → max_s
  если jitter > 0 → d = clamp(d × uniform(1−jitter, 1+jitter), 0, max_s)
  вернуть Duration(d)
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| `max_attempts = 1` | «Повторить» сразу даёт «Ошибка» (как раньше) |
| Пауза 0 | Повтор без ожидания, но через «Ожидает повтора» → «Принята» |
| Задержка «отложить» 0 без возможности источника | Немедленный перезапуск в процессе |
| Остановка во время повторного ожидания слота | «Отменена» из «Принята», как ожидание слота при приёме |
| Ack «после приёма» и повтор | Ack уже выполнен; повторы его не трогают |
