## Context

В ядре уже есть модель задачи (`task-model-and-lifecycle`): `Task<Args>`, `TaskId`, `AckPoint`, `Metadata`, `MetadataRegistry`, `PushOutcome`. Воркера и очереди ещё нет. Эта заявка задаёт контракт, по которому они будут работать с любым источником, и даёт эталонную реализацию в памяти.

Требования (спецификация `openspec/specs/taskcraft/taskcraft.md`):

- 2.3.1 — у опроса три ответа и ошибка; «пусто» нельзя выразить через «закрыт».
- 2.3.9 — момент ack. Для журнала ack — это граница фиксации смещения (п. 5). У хранилища момент ack не настраивается (п. 6).
- 2.3.10 — переопределение момента ack на задаче допустимо только у источника с поштучным ack, кроме хранилища.
- 2.5 «Источник» — операции: опрос, приём постановки, пробуждение, ack, отложить; возможности; кодек.
- 2.6 «In-memory источник» — табличный, ограниченная ёмкость, приём постановки, отложенный повтор, пробуждение при постановке.
- Критерии: спецификация №24, №47; критерии заявки 1–3.

Разбор apalis подсказывает, чего избегать: `Ready(None)` как необратимый EOF (A-1), один слот waker'а и гонка `poll_ready`/`poll_next` (A-5), паника и неограниченный рост в in-memory бэкенде (B-3).

## Goals / Non-Goals

**Goals:**

- Публичный трейт `Source` с тремя ответами опроса, ack по квитанции, необязательными постановкой, отложенным повтором и пробуждением.
- Возможности источника как данные и проверка переопределения момента ack (2.3.10).
- Трейт `Codec` и две реализации: тождественный кодек (in-memory) и JSON-кодек с метаданными через реестр.
- Помощник границы фиксации смещений для журнальных источников (2.3.9 п. 5).
- `InMemorySource<Args>`: корректный при многих продюсерах и потребителях, без неограниченного роста, с пробуждением без потерянных сигналов.

**Non-Goals:**

- Воркер, который опрашивает источник и вызывает ack в нужный момент, — `worker-loop-and-supervision`.
- Постановка через очередь с проверкой реестра задач и `PushOutcome` — `task-registry`. Здесь источник отвечает только за свою часть: запись, дубль по идентификатору, заполненность.
- Обязательность хука восстановления при моменте «после приёма» — `ownership-and-recovery`.
- Источник Kafka и хранилище — свои заявки.

## Decisions

### Асинхронный трейт `Source` с методами на `&self`

**Решение**:

```rust
pub trait Source: Send + Sync + 'static {
    type Message: Send + 'static;
    type Receipt: Send + 'static;
    type Error: std::error::Error + Send + Sync + 'static;

    fn capabilities(&self) -> Capabilities;
    fn poll(&self) -> impl Future<Output = Result<Polled<Self::Message, Self::Receipt>, Self::Error>> + Send;
    fn ack(&self, receipt: Self::Receipt) -> impl Future<Output = Result<(), Self::Error>> + Send;

    // Необязательные, по умолчанию «не поддерживается» / «нет пробуждения»:
    fn subscribe(&self) -> Option<WakeSignal> { None }
    fn push(&self, id: &TaskId, message: Self::Message)
        -> impl Future<Output = Result<PushResult, PushError<Self::Error>>> + Send;
    fn defer(&self, receipt: Self::Receipt, message: Self::Message, at: tokio::time::Instant)
        -> impl Future<Output = Result<(), DeferError<Self::Error>>> + Send;
}
```

- `Polled<M, R>` — `Task { message, receipt }`, `Empty`, `Closed(CloseReason)`.
- Квитанция (`Receipt`) — то, чем источник узнаёт выдачу при ack и defer: номер выдачи, смещение, ключ строки.

**Обоснование**:
- Три ответа — отдельные варианты, поэтому A-1 невыразим (2.3.1 п. 6).
- Методы на `&self`: ack приходит из задач, которые завершаются параллельно с опросом. Источник разделяется через `Arc` и сам отвечает за синхронизацию, как клиенты Kafka и пулы соединений СУБД.
- `impl Future + Send` в трейте (стабильно с 1.75, MSRV 1.99) даёт асинхронные методы без боксинга и без макросов. Воркер обобщён по `S: Source`, поэтому объектная безопасность не нужна.

**Альтернативы**:
- Poll-based `poll_next(Pin<&mut Self>, &mut Context)`, как у apalis — отклонено. Ручная работа с `Waker` — ровно то место, где у apalis появился «один слот waker'а» (A-5). Асинхронный метод перекладывает пробуждения на tokio.
- `&mut self` — отклонено: заставило бы сериализовать ack через опрос.
- `async-trait` — отклонено: лишняя зависимость и боксинг каждого вызова.

### Возможности — данные, проверка переопределения ack — функция

**Решение**:
- `Capabilities` (`#[non_exhaustive]`, `Copy`) с конструктором `Capabilities::new(AckPointSupport)` и методами `with_push()`, `with_defer()`, `with_transactional_ack()`. Чтение — `accepts_push()`, `supports_defer()`, `ack_point_support()`, `transactional_ack()`.
- `AckPointSupport`:
  - `PerTask` — in-memory: момент ack задаётся на очереди и может быть переопределён задачей;
  - `QueueOnly` — журнал: только на очереди;
  - `Fixed` — хранилище: момент ack не настраивается.
- `Capabilities::check_ack_override(Option<AckPoint>) -> Result<(), AckOverrideUnsupported>`: переопределение без `PerTask` → ошибка «ack point override is not supported by this source».

**Обоснование**: 2.3.10 различает три случая (in-memory, хранилище, журнал), а одного флага «поштучный ack» для этого мало: хранилище ack поштучно, но переопределение запрещает. Возможности нужны во время исполнения, потому что ошибки 2.11.2 возникают при постановке.

**Альтернативы**:
- Маркерные трейты на каждую возможность — отклонено: очередь и воркер обобщены по одному `S: Source`, и разветвление по наличию трейта без специализации невыразимо.

### Кодек — отдельный трейт, по значению

**Решение**:
- `Codec<Args, M>: Send + Sync + 'static` с `encode(&self, Task<Args>) -> Result<M, CodecError>` и `decode(&self, M) -> Result<Task<Args>, CodecError>`.
- `IdentityCodec` — для источников, которые хранят `Task<Args>` как есть (in-memory). Метаданные остаются типизированными (2.3.17 п. 2).
- `JsonCodec { registry: MetadataRegistry }` — `M = Vec<u8>`. Конверт JSON: `{"id", "args", "metadata", "attempt", "retries", "ack_point"}`; метаданные кодируются через реестр. При декодировании метаданные кладутся сырыми и разбираются лениво (2.3.17 п. 5). Ошибка разбора конверта или аргументов — `CodecError::Decode`: это отравленное сообщение (2.3.13).
- Для собственных кодеков у задачи появляются `Task::into_parts()` и `Task::from_parts(TaskParts<Args>)`. `TaskParts` — открытая структура со всеми полями, включая счётчики: кодек восстанавливает задачу полностью.

**Обоснование**: 2.5 «Кодек»; кодек по умолчанию — JSON (глоссарий 1.2). По значению — потому что задача целиком переходит в источник, а копировать аргументы незачем. Kafka и хранилище переиспользуют `JsonCodec`.

**Альтернативы**:
- Кодек внутри источника — отклонено: один источник Kafka с разными форматами сообщений потребовал бы разных типов источника.
- Публичные сеттеры счётчиков у `Task` — отклонено: `from_parts` явно говорит «собираю задачу целиком», а не «правлю номер попытки».

### Пробуждение без потерянных сигналов — счётчик через `watch`

**Решение**: `WakeSignal` оборачивает `tokio::sync::watch::Receiver<u64>`.
- Источник увеличивает счётчик при каждой постановке и при закрытии.
- `WakeSignal::mark_seen()` запоминает текущее значение.
- `WakeSignal::changed()` завершается сразу, если счётчик менялся после `mark_seen()`, иначе ждёт изменения. Возвращает `false`, если источник уничтожен.
- Порядок для воркера: `mark_seen()` → `poll()` → при «пусто» `changed()`. Постановка между опросом и ожиданием не теряется.

**Обоснование**: «пробуждение» из 2.5 без гонки «проверил — уснул». `watch` поддерживает любое число подписчиков, так что «одного слота waker'а» (A-5) нет.

**Альтернативы**:
- `Notify::notify_waiters` — отклонено: сигнал, пришедший до начала ожидания, теряется.
- `Notify::notify_one` — отклонено: будит одного из нескольких воркеров, а нужно всех.

### Граница фиксации смещений — `OffsetTracker`

**Решение**: помощник для журнальных источников, один экземпляр на раздел.
- `delivered(offset)` — смещение выдано.
- `acked(offset)` — смещение подтверждено.
- `commit_point() -> Option<i64>` — наибольшее N такое, что все выданные смещения ≤ N подтверждены. `None`, пока подтверждённого непрерывного префикса нет.
- Хранит только выданные и неподтверждённые смещения плюс максимум и начало, поэтому память ограничена числом задач в работе.

**Обоснование**: 2.3.9 п. 5 и критерий заявки №3. Правило общее для любого журнала, поэтому оно в ядре, а не в `taskcraft-kafka`.

### `InMemorySource<Args>`

**Решение**:
- `Message = Task<Args>`, `Receipt = Delivery` (непрозрачный номер выдачи), `Error = Infallible`.
- Состояние под `std::sync::Mutex`: короткие участки, без `await` внутри.
  - `ready: VecDeque<Task<Args>>`;
  - `deferred: BTreeMap<(Instant, u64), Task<Args>>`;
  - `in_flight: HashMap<u64, TaskId>`;
  - `ids: HashSet<TaskId>` — все удерживаемые задачи (готовые, отложенные, выданные);
  - `closed: bool`, `next_delivery: u64`.
- `capacity` из конструктора, `>= 1`.
- **Опрос:** перенести наступившие отложенные в `ready`, выдать первую готовую в `in_flight`. Иначе `Closed`, если источник закрыт, а готовых и отложенных нет. Иначе `Empty`.
- **Ack:** удалить выдачу и идентификатор. Повторный ack неизвестной квитанции — `Ok`: ack идемпотентен.
- **Постановка:** закрыт → `PushError::Closed`; идентификатор удерживается → `PushResult::Duplicate`; `ids.len() == capacity` → `PushResult::Full`; иначе в `ready`, `PushResult::Stored`, счётчик пробуждения +1.
- **Отложить:** выдача убирается из `in_flight`, задача кладётся в `deferred` с моментом доставки; идентификатор остаётся удерживаемым.
- `close()` запрещает постановку, будит ждущих; `len()` — число удерживаемых задач.
- Возможности: `PerTask`, приём постановки, отложенный повтор.
- Время — `tokio::time::Instant`, чтобы отложенные задачи работали на виртуальном времени в тестах.

**Обоснование**: 2.6 и критерии №47 и заявки №2. Мьютекс с короткими участками проще и надёжнее lock-free для эталона. Удерживаемые идентификаторы и выдачи удаляются на ack и defer, поэтому структуры не растут после выдачи всех задач — в отличие от вечно растущего набора ключей apalis (B-3).

**Альтернативы**:
- `tokio::sync::Mutex` — отклонено: внутри участков нет `await`.
- Ёмкость без учёта выданных — отклонено: тогда медленный обработчик позволял бы держать в памяти неограниченно много задач.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| `impl Future` в трейте не объектно-безопасен | `dyn Source` невозможен | Воркер обобщён по `S: Source`; при необходимости позже — отдельная обёртка с боксингом |
| Отложенная задача наступает без постановки и не будит воркер | Воркер увидит её только при следующем опросе по стратегии | Стратегия опроса (`interruptible-poll-strategies`) ограничивает задержку; поведение задокументировано |
| `tokio` в ядре — первая тяжёлая зависимость | Новые записи cargo-vet | Возможности `sync` и `time` без `rt` в основных зависимостях; tokio покрыт импортированными аудитами или исключением |
| `Capabilities` с `non_exhaustive` | Собственные источники строят возможности только через конструктор | Конструктор и `with_*` покрывают все поля |

## Архитектура

### Компонентная диаграмма

```
                   ┌───────────── Source (трейт) ─────────────┐
 воркер (позже) ── │ poll → Polled{Task|Empty|Closed}          │
                   │ ack(receipt)   subscribe → WakeSignal     │
                   │ push(id, msg) → PushResult (если умеет)   │
                   │ defer(receipt, msg, at)    (если умеет)   │
                   │ capabilities → Capabilities               │
                   └───────────────────────────────────────────┘
                        ▲                         ▲
            InMemorySource<Args>          собственные / taskcraft-kafka / хранилище
            (Message = Task<Args>)                (Message = Vec<u8>)
                        ▲                         ▲
                  IdentityCodec               JsonCodec(MetadataRegistry)
                                                  OffsetTracker (журналы)
```

## Детали реализации

### Алгоритмы

```
OffsetTracker:
  start = None; max = None; pending = упорядоченное множество
  delivered(o): start = min(start, o); max = max(max, o); pending.add(o)
  acked(o):     pending.remove(o)
  commit_point:
    если start = None → None
    если pending пусто → max
    иначе p = min(pending); если p = start → None иначе p − 1
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| Опрос пустого незакрытого in-memory источника | `Empty`, сколько угодно раз подряд |
| Закрыт, но есть отложенные | `Empty`, пока они не наступят и не будут выданы; затем `Closed` |
| Постановка дубля по идентификатору, который выдан и не подтверждён | `Duplicate` |
| Ack неизвестной квитанции | `Ok`: ack идемпотентен |
| `capacity = 0` | Паника в конструкторе с понятным сообщением: ёмкость — ошибка программиста, проверка конфигурации очереди появится вместе с очередью |
| Конверт JSON без поля `attempt` | Ошибка декодирования: конверт — контракт формата |
| Метаданные конверта — не объект | Ошибка декодирования |

|---------------|----------|
| `Capabilities::check_ack_override` | Без переопределения — всегда `Ok`; с переопределением: `PerTask` — `Ok`, `QueueOnly` и `Fixed` — ошибка (критерий №24) |
| `OffsetTracker` | Выданы 1–3, подтверждены 1 и 3 → граница 1; после 2 → 3 (критерий заявки №3); пустой трекер → `None`; подтверждён только не первый → `None` |
| `JsonCodec` | Кругооборот задачи с идентификатором, счётчиками, моментом ack, метаданными; незарегистрированный тип → `Encode`; битый JSON и не-объект метаданных → `Decode` |
| `IdentityCodec` | Задача проходит без изменений, метаданные остаются типизированными |
| `InMemorySource` | Постановка до ёмкости и сверх неё → `Full` (критерий №47); дубль → `Duplicate`; опрос пустого → `Empty`; закрытый и пустой → `Closed`; ack освобождает место; defer → задача снова выдаётся после наступления момента (виртуальное время) |
| `WakeSignal` | Постановка между `mark_seen` и `changed` не теряется |
