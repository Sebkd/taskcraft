## Context

Что есть сейчас:

- **Исход задачи** принимается в `worker/execute.rs`: `execute` → `run_once` → `decide` даёт `Next::Finish(state, reason)`, затем `finish` пишет журнал, событие `Finished`, снимает задачу с учёта и делает ack или `complete`.
- **«Ошибка»** — исход «прервать», исчерпанные попытки, тайм-аут попытки при `TimeoutOutcome::Abort`, отказ извлечения. **«Паника»** — паника обработчика.
- **Хуки очереди** — синхронные замыкания `Fn(…) + Send + Sync` под `catch_unwind`: `reject_with`, `dead_letter`. Хук dead-letter получает структуру `DeadLetter { queue, message, error }`.
- **Тип аргументов и контекст.** `ExecCtx<S, C>` общий для задач очереди и от типа аргументов не зависит. У `execute` семь параметров, это предел clippy `too_many_arguments`.
- **Терминальные состояния.** «Завершена», «Ошибка», «Паника», «Отменена» — по глоссарию «после них ничего не следует». Таблица `Lifecycle` (`state.rs`) и тест `no_way_out_of_states_that_end_the_task` это закрепляют.
- **Хранилище** держит завершённые задачи до конца срока хранения: состояние, `attempt`, `retries`, `reason`. Опрос берёт `state IN ('queued','deferred')`, а счётчики накладывает на конверт из колонок.

## Decisions

### D-1. Хук «задача с ошибкой»

- **Построитель:** `QueueBuilder::failed_task(hook)`, где `hook: Fn(FailedTask<Args>) + Send + Sync + 'static`. Имя и форма — по образцу `dead_letter`.
- **Что получает хук** — `FailedTask<Args>` (публичная, `#[non_exhaustive]`, поля открыты для чтения):
  - `queue: String`;
  - `task: Task<Args>` — аргументы, метаданные, номер попытки;
  - `state: TaskState` — «Ошибка» или «Паника»;
  - `reason: FinishReason`.
- **Когда вызывается:** в `execute` на ветке `Next::Finish`, при «Ошибке» или «Панике», **до** `finish`. Значит, до журнала исхода, события `Finished` и ack/`complete`: если процесс упадёт в хуке, задача не подтверждена. Задача передаётся хуку перемещением, без копии.
- **Паника хука** ловится `catch_unwind`. Дальше:
  - журнал ERROR `task/failed_hook_failed`: `failed-task hook panicked: queue={}, task_id={}`;
  - исход и ack задачи не меняются (критерий №2).
- **Как хук доходит до `execute`.** Хук зависит от `Args`, `ExecCtx` — нет. Хук передаётся в `execute` параметром `Option<FailedFn<Args>>`, а пара «квитанция, ack позже» складывается в одну структуру `Delivered<S>`. Так параметров остаётся семь.
- **Отмена.** «Отменена» хук не вызывает: это не ошибка, и причина приходит от потребителя или от остановки.

### D-2. Повторный запуск: `QueueHandle::requeue(id)`

- **Сигнатура:** `requeue(&TaskId) -> Result<(), RequeueError>`.
- **`RequeueError`** (`#[non_exhaustive]`):
  - `NotFailed(TaskState)` — задача есть, но не в «Ошибке» или «Панике»: живая, «Завершена», «Отменена» (критерий №4);
  - `Unknown` — задачи нет. Сюда же попадают источники без истории, например in-memory: там завершённые задачи не хранятся;
  - `Source(BoxError)`.
- **Контракт хранилища:** `TaskStore::requeue(id) -> Result<Requeue, Error>`, где `Requeue::{Requeued, NotFailed(TaskState), NotFound}`. Реализация по умолчанию даёт `NotFound`: трейт уже опубликован, метод добавляется совместимо. `Backend::requeue` у потока и источника с постановкой — `NotFound`, у хранилища пересылает вызов.
- **Сначала проверяется своя очередь.** Ручка смотрит, есть ли задача среди живых этого процесса. Если есть — `NotFailed(state)` без обращения к базе.
- **PostgreSQL, одним оператором:**
  - `UPDATE … SET state = 'queued', retries = 0, reason = NULL, owner = NULL, lease_until = NULL, next_delivery = NULL, updated_at = now() WHERE queue, id AND state IN ('failed','panicked')`;
  - `attempt` сохраняется: следующая попытка продолжает нумерацию (критерий №3);
  - строк 0 — состояние читается, чтобы различить `NotFailed` и `NotFound`;
  - после успеха — пробуждение и журнал INFO `task/requeued`: `task requeued: queue={}, task_id={}`.
- **Срок хранения** не меняется: вернуть можно задачу, ещё не удалённую по сроку.

### D-3. Терминальность и переход 2.4.1.14

- Заявка добавляет переход «Ошибка/Паника → В очереди». Он противоречит определению терминального состояния: «после него ничего не следует».
- **Решение:**
  - переход выполняет **только хранилище** по явной команде потребителя;
  - в жизненном цикле задачи **внутри процесса** состояния остаются терминальными. Таблица `Lifecycle` и её тесты не меняются;
  - возвращённая задача — новая доставка той же записи: процесс принимает её опросом с `Lifecycle::queued()` → «Принята», как обычную (переход 2.4.1.12 → 2.4.1.1).
- **В спецификации:**
  - глоссарий: «терминальное — в процессе после него ничего не следует; хранилище может вернуть задачу с ошибкой в очередь (2.3.26)»;
  - таблица 2.4.1 получает строку 2.4.1.14 с пометкой «только хранилище».

### D-4. Наблюдатель и метрики

- Новых событий нет: исход уже идёт событием `Finished`.
- Возврат в очередь виден по журналу INFO и по последующему событию `Pushed`, которое ручка отправляет так же, как при постановке. Ряды метрик 4.4 не меняются.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Долгий хук задерживает освобождение слота | Задача держит слот и пулы на время хука | Документация: хук синхронный и быстрый — тяжёлое отправлять из порождённой задачи (как у `reject_with`) |
| Возврат задачи, которая падает всегда | Повторные исходы «Ошибка» | Это решение потребителя; номер попытки растёт и виден в статусе |

## Тестирование

| Критерий | Проверка |
|----------|----------|
| №1 | Тест ядра: попытки исчерпаны → хук получил задачу (аргументы, метаданные) и «попытки исчерпаны»; «прервать» и паника — тоже; «Завершена» и «Отменена» — хук не вызван |
| №2 | Тест ядра: хук паникует → ERROR `task/failed_hook_failed`, событие `Finished` «Ошибка», ack выполнен (`FaultySource` считает ack) |
| №3 | Тест хранилища: «прервать» → `requeue` → «В очереди», исполнена снова, номер попытки 2, `retries` 0 |
| №4 | Тест хранилища: `requeue` «Завершена» → `NotFailed(Succeeded)`; живой → `NotFailed(Running)`; неизвестной → `Unknown`. Ядро: in-memory → `Unknown` |
