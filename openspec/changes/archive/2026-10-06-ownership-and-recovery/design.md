## Context

После `task-registry` у очереди есть реестр живых задач, ручка с постановкой, статусом и отменой, у каждой задачи свой признак отмены. Монитор (`Monitor::run`) сразу запускает воркеры: стадии «Запуск» (2.4.2) с хуком восстановления нет. Попытка не ограничена по времени.

Требования:

- **2.3.18, 2.2.8, переходы 2.4.2.1, 2.4.2.2, 2.4.2.10, 2.4.2.11.** Хук восстановления до приёма. Ошибка хука — монитор не стартует. Сигнал остановки во время хука прерывает его.
- **2.3.9 п. 4, 2.10.** Момент ack «после приёма» без хранилища требует хук: «ack-on-accept without a store requires a recovery hook».
- **2.3.7 п. 6.** Восстановленные задачи не отвергаются: при отсутствии слота ждут его вне лимита ожидания.
- **2.3.16, 2.1.2.13, 2.3.15 п. 4.** Таймаут попытки от её начала. Итог задаёт настройка очереди, а не ответ обработчика.
- **2.3.19 п. 3.** Сирота без хранилища — задача, которой нет в реестре; признак даёт запрос статуса (уже есть).
- **Критерии:** спецификация №22, №26, №36, №46; критерии заявки №1, №2.

---

## Goals / Non-Goals

**Goals:**

- `QueueBuilder::recover_with(hook)` и `QueueBuilder::no_recovery()`.
- Двухфазный `Monitor::run`: сначала хуки всех очередей, затем воркеры. Тип результата — `Result<ShutdownReport, RecoveryError>`.
- Проверка «ack после приёма требует хук» в `QueueBuilder::build`.
- `QueueBuilder::attempt_timeout` и `QueueBuilder::timeout_outcome(TimeoutOutcome)`.

**Non-Goals:**

- Сироты и аренда в хранилище — `durable-task-store`.

## Decisions

### Хук восстановления — `FnOnce` на очереди

**Решение**: `recover_with<F, Fut, E>(hook)`, где `F: FnOnce() -> Fut`, `Fut: Future<Output = Result<Vec<Task<Args>>, E>>`, `E: Into<BoxError>`. Хранится в `Queue::recovery` как `RecoveryFn<Args>`. Монитор вызывает хук один раз.

**Обоснование**: монитор запускается один раз (из «Остановлен» переходов нет), поэтому `FnOnce` достаточно и позволяет переносить в хук владеемые ресурсы.

### `no_recovery()` — явный отказ от восстановления

**Решение**: хук, возвращающий пустой список. Проверка 2.10 его принимает.

**Обоснование**: правило 2.3.9 п. 4 запрещает **молчаливую** потерю принятых задач. Есть очереди, где потеря допустима: задачи дешёвые или отправитель повторит. Явный вызов фиксирует это решение в коде. Без него очередь с ack «после приёма» на in-memory или журнальном источнике не строится.

**Альтернативы**:
- Только `recover_with(|| async { Ok(vec![]) })` — отклонено: многословно для частого случая, решение не названо.

### Двухфазный старт монитора

**Решение**: `register` превращает очередь в `StartFn`: она вызывает хук, пишет INFO `recovery/recovered` и возвращает `WorkerFn` с восстановленными задачами. `run` вызывает `StartFn` всех очередей по порядку регистрации, каждый — в `select!` с сигналом остановки.

| Исход хуков | Результат `run` |
|-------------|-----------------|
| Все успешны | Воркеры запускаются, `Ok(ShutdownReport)` по завершении |
| Ошибка хука | ERROR `recovery/failed`, ни один воркер не стартует, `Err(RecoveryError)` (2.4.2.10) |
| Сигнал остановки во время хука | Хук прерван, ни один воркер не стартует, `Ok(ShutdownReport)` с причиной «остановка» у всех очередей (2.4.2.11) |

В двух последних случаях реестры всех очередей получают «очередь останавливается»: постановка через ручку отвечает ошибкой.

**Обоснование**: 2.2.8 — начинать приём без восстановления значит потерять задачи. Хуки идут до запуска любого воркера, поэтому ошибка одной очереди не оставляет другие работающими.

### Восстановленные задачи в воркере

**Решение**: `run_worker` получает `recovered: Vec<Task<Args>>` и до первого опроса для каждой задачи:

1. `try_accept` в реестре; занятый идентификатор → DEBUG `task/duplicate`, задача пропускается.
2. Слот занимается сразу, если свободен; иначе `Slot::Wait { place: None }` — ожидание вне лимита, без хука отказа.
3. `execute` с квитанцией `None` и без ack «после завершения»: задачи нет в источнике.

Квитанция в `execute`, `decide` и `finish` становится `Option<S::Receipt>`. «Отложить» восстановленной задачи выполняется в процессе: возвращать источнику нечего.

### Таймаут попытки — свой признак у каждой попытки

**Решение**:
- `execute` создаёт для каждой попытки `attempt_cancel = cancel.child_token()`. Его получает обработчик через `Cancel`.
  - Отмена задачи (запрос, остановка) выставляет признак попытки через родителя.
  - Таймаут выставляет только признак попытки: следующая попытка при «повторить» получает чистый признак.
- `select!` попытки получает третью ветку `expire`: `sleep(timeout)` → флаг `timed_out`, WARN `task/timed_out`, `attempt_cancel.cancel()`, затем `sleep(cancel_grace)` → прерывание.
- Итог попытки:

| Условие | Итог |
|---------|------|
| Паника | «Паника» |
| Признак задачи выставлен | «Отменена» с причиной из реестра |
| `timed_out`, исход «прервать» | «Ошибка», `AttemptTimeout` |
| `timed_out`, исход «повторить» | Как `Outcome::Retry { AttemptTimeout }`: пауза или «попытки исчерпаны» |
| Иначе | По ответу обработчика |

**Обоснование**: 2.3.15 п. 4 и критерий №46 — ответ прерванного обработчика не важен.

### `Monitor::run` возвращает `Result`

**Решение**: `Result<ShutdownReport, RecoveryError>`. `RecoveryError` хранит имя очереди и ошибку хука как источник; сообщение `recovery failed: queue=<имя>: <ошибка>`.

**Обоснование**: 2.2.8 и 2.11.1 — монитор возвращает ошибку. Публичных версий ещё нет.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Проверка 2.10 ломает очереди с ack по умолчанию | Каждая in-memory очередь без хука перестаёт строиться | `no_recovery()` — одна строка; сообщение ошибки называет причину |
| Хуки выполняются последовательно | Старт дольше при многих очередях | Хуки — разовая работа при старте; порядок предсказуем |
| Переопределение ack «после приёма» на задаче при очереди «после завершения» | Такая задача теряется при падении без хука | Проверка 2.10 — настройка очереди; переопределение на задаче — решение отправителя |

## Архитектура

```
Monitor::run
  ├─ для каждой очереди: select{ stop | StartFn() }
  │     StartFn: hook() → INFO recovery/recovered → WorkerFn(recovered)
  │     ошибка → ERROR recovery/failed, close_all, Err(RecoveryError)
  │     stop   → close_all, Ok(отчёт «остановка»)
  └─ запуск воркеров
run_worker: восстановленные → try_accept → слот или ожидание вне лимита → execute(receipt=None)
execute: attempt_cancel = cancel.child_token()
         select{ попытка | forced_abort(отмена запросом) | expire(таймаут + grace) }
```

## Изменения в коде

### Новые модули / классы / функции

| Имя | Расположение | Назначение |
|-----|--------------|------------|
| `TimeoutOutcome` | `queue.rs` | Итог таймаута: `Abort` (по умолчанию), `Retry` |
| `RecoveryError` | `error.rs` | Ошибка хука восстановления |
| `ConfigError::RecoveryRequired` | `error.rs` | Ack «после приёма» без хука и без хранилища |
| `expire` | `worker.rs` | Ветка таймаута попытки |

### Изменения в существующих сущностях

| Имя | Расположение | Изменение |
|-----|--------------|----------|
| `QueueBuilder` | `queue.rs` | `recover_with`, `no_recovery`, `attempt_timeout`, `timeout_outcome`; проверки в `build` |
| `Monitor` | `monitor.rs` | `register` строит `StartFn`; `run` двухфазный, возвращает `Result` |
| `run_worker` | `worker.rs` | Параметр `recovered`; приём восстановленных до первого опроса |
| `execute`, `decide`, `finish` | `worker.rs` | `Option<S::Receipt>`; признак попытки; таймаут |
