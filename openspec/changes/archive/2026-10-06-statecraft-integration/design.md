## Context

Обработчик сегодня возвращает исход сразу (`IntoOutcome`: `()`, `Outcome`, `Result<(), TaskError>`, `Result<Outcome, TaskError>`). У каждой попытки есть свой признак отмены (`TaskRequest::cancel_token`). Его выставляют запрос отмены, таймаут попытки и остановка, а по истечении льготного времени future попытки уничтожается (`worker.rs`, `forced_abort` / `expire`). Паника future попытки — исход «паника» (`run_attempt`).

statecraft-fsm 0.2 (crates.io) в нынешнем виде:
- макрос `#[fsm]` генерирует конкретные типы автомата, общего трейта над ними нет;
- в режиме `spawn` (возможность `tokio`) автомат живёт в своей задаче, управление идёт через клонируемый `Handle` (`send`, `watch`, `shutdown`);
- `spawn` возвращает `JoinHandle<()>`, контекст наружу не выходит;
- дойдя до финального состояния, задача автомата не завершается: она ждёт событий до `shutdown`.

Требования:
- **2.3.21** — расширяемый контракт «запустить, мягко остановить, дождаться исхода, перевести исход»; признак отмены → мягкая остановка; паника → «паника»; таймаут, отмена и прерывание действуют как на обработчик; адаптер к statecraft-fsm в нынешнем виде (исход через контекст).
- **Критерии:** спецификация №35; критерии заявки №1, №2.

---

## Goals / Non-Goals

**Goals:**

- Трейт `Runnable`, обёртка `Run<R>` для возврата из обработчика, трейт `HandlerOutput` над всем, что обработчик может вернуть.
- Адаптер `SpawnedMachine` и слот исхода `OutcomeSlot` для автомата в собственной задаче.

**Non-Goals:**

- Возможность сборки «statecraft» с общей реализацией для всех автоматов с терминальным исходом — после заявки `terminal-state-outcome` в statecraft-fsm. Пустую возможность сейчас не заводим.

## Decisions

### `Runnable` — один асинхронный метод и перевод исхода

**Решение**:

```rust
pub trait Runnable: Send + 'static {
    type Output: Send;
    fn run(self, stop: CancellationToken) -> impl Future<Output = Self::Output> + Send;
    fn into_outcome(output: Self::Output) -> Outcome;
}
```

Как четыре части контракта 2.3.21 ложатся на трейт:

| Часть контракта | В трейте |
|-----------------|----------|
| «Запустить» и «дождаться исхода» | `run` |
| «Мягкая остановка» | признак `stop`: это признак отмены попытки |
| «Перевести исход» | `into_outcome` |

**Обоснование**: в Rust запуск и ожидание — один future. Признак отмены уже есть у попытки, и таймаут, отмена и прерывание действуют на запускаемое без нового кода в воркере (2.3.21 п. 5).

### `HandlerOutput` вместо `IntoOutcome` в ограничении обработчика

**Решение**: `impl_handler!` требует `R: HandlerOutput`. Реализации:

| Тип | Что делает `finish` |
|-----|---------------------|
| Любой `T: IntoOutcome` | Готовый исход |
| `Run<R: Runnable>` | Запускает `R` с признаком отмены попытки |
| `Result<Run<R>, TaskError>` | `Err` — исход ошибки, `Ok` — запуск |

Перед `into_task` обработчик забирает признак отмены попытки из запроса. `#[diagnostic::on_unimplemented]` переносится на `HandlerOutput` с полным списком.

**Обоснование**: «обработчик вернул запускаемое» (2.3.21) — буквально тип возврата. Перекрытия реализаций нет: `IntoOutcome` локальный, `Run` и `Result<Run<_>, _>` его не реализуют.

### Адаптер «в нынешнем виде»: `SpawnedMachine` + `OutcomeSlot`

**Решение**:
- `OutcomeSlot` — `Arc<watch::Sender<Option<Outcome>>>`; клон кладётся в контекст автомата, финальные состояния вызывают `set`.
- `SpawnedMachine::new(join, slot, stop)`, где `stop` — функция мягкой остановки потребителя: отправить событие остановки или вызвать `handle.shutdown()`.
- `run`:
  1. Ждёт первое из трёх: исход в слоте, конец задачи автомата, признак отмены.
  2. При признаке отмены вызывает `stop` один раз и дальше ждёт исход или конец задачи.
- `MachineEnd` переводится так:

| Как закончилось | Исход |
|-----------------|-------|
| Исход в слоте | Этот исход |
| Задача кончилась без исхода | «Прервать» (`machine stopped without an outcome`) |
| Паника в задаче автомата | «Паника» с сообщением |

- `AbortOnDrop` прерывает задачу автомата, когда `run` закончился или его future уничтожен по льготному времени.

**Обоснование**: автомат statecraft-fsm сам не завершает задачу в финальном состоянии, поэтому исход сигналит слот, а не `JoinHandle`. Адаптеру не нужна зависимость от statecraft-fsm, и ядро остаётся без неё (инвариант 1.3.14, критерий заявки №2). Сообщение исхода через контекст — то, что 2.3.21 п. 4 называет «нынешним видом».

### Проверка на настоящем автомате и запрет зависимости в CI

**Решение**:
- statecraft-fsm 0.2 (`tokio`) — только dev-dependency `taskcraft`.
- Новый шаг CI «Core dependency tree»: `cargo tree -p taskcraft -e normal --all-features` не содержит `rdkafka`, `statecraft`, `sqlx`, `postgres`.

**Обоснование**: критерий №33 и критерий заявки №2 проверяются автоматически, а не на глаз.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Потребитель забыл `set` в финальном состоянии | Задача ждёт до таймаута или отмены | Без таймаута — до отмены; документация `SpawnedMachine`; общая реализация после изменения statecraft-fsm уберёт ручной слот |
| `stop` не приводит автомат к финалу | Прерывание по льготному времени | Поведение 2.3.15 п. 3 |

## Тестирование

### Unit-тесты (`runnable.rs`)

| Сценарий |
|----------|
| Исход из слота; нет исхода — «прервать»; паника — «паника» |
| Признак отмены вызывает мягкую остановку один раз |
| Уничтожение `run` прерывает задачу автомата |
| `Result<Run<_>, TaskError>` с ошибкой — исход ошибки |
