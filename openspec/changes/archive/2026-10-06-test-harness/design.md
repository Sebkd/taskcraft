## Context

В ядре уже есть контракт источника (`Source`, `InMemorySource`, `WakeSignal`, `Codec`) и обработчики (`task_fn`, `run_attempt`, `Outcome`, `TaskError`). Воркера ещё нет: он появится в `worker-loop-and-supervision`. Харнесс должен прийти **до** воркера, чтобы воркер с первого дня проверялся на дефектах, которые дожили у apalis до rc.9 из-за отсутствия таких тестов (P-1).

Требования:

- Спецификация 4.3 п. 8 — виртуальное время и тестовый источник с внедрением трёх видов сбоев: ошибка декодирования, ошибка источника, обрыв между исполнением и ack.
- Спецификация 4.2 — ограниченные служебные структуры и отсутствие активного ожидания.
- Критерии заявки:
  1. каждый сбой воспроизводится детерминированно;
  2. отчёт о дублях и потерях;
  3. сценарии четырёх известных дефектов падают на заглушках с этими дефектами;
  4. сценарий «отмена во время паузы повтора» проходит на виртуальном времени.

Чтобы сценарии пережили появление воркера, они проверяют **любой** воркер через узкий интерфейс «запусти цикл на этом источнике». Сейчас его реализуют заглушки в тестах, позже — настоящий воркер.

---

## Goals / Non-Goals

**Goals:**

- Модуль `taskcraft::testing` за возможностью сборки `test-util`.
- `FaultySource` — источник, управляемый сценарием: постановка задач, отравленные сообщения, N ошибок опроса, N ошибок ack с повторной доставкой.
- `FaultyCodec` — декодирование отравленного сообщения в ошибку.
- `DeliveryLedger` — учёт поставленных и исполненных задач, отчёт о дублях и потерях.
- Сценарии `scenarios::*` для воркера и для источника, возвращающие `Result<(), ScenarioFailure>`.
- Заглушки с дефектами и эталонный воркер в тестах: каждый сценарий падает на своей заглушке и проходит на эталоне.

**Non-Goals:**

- Настоящий воркер — `worker-loop-and-supervision`. Его тесты будут вызывать эти же сценарии.
- Внедрение сбоев в Kafka или в хранилище — их собственные заявки.

## Decisions

### Харнесс — публичный модуль за возможностью `test-util`

**Решение**: `taskcraft::testing` компилируется только с возможностью `test-util` (по образцу tokio). Интеграционные тесты харнесса помечены `#![cfg(feature = "test-util")]`; CI запускает тесты с `--all-features`.

**Обоснование**: спецификация 4.3 п. 8 — «в составе библиотеки», то есть доступен и потребителю для тестов его обработчиков. За возможностью — чтобы не попадать в обычную сборку.

**Альтернативы**:
- Отдельный пакет `taskcraft-test` — отклонено: сценариям нужен доступ к тем же типам; отдельный пакет удвоит публикацию ради одного модуля.
- Только `#[cfg(test)]` — отклонено: потребитель не смог бы им пользоваться.

### `FaultySource` и `FaultyCodec`

**Решение**:
- `FaultySource<Args>` реализует `Source` с `Message = Scripted<Args>`. `Scripted` — это `Task(Task<Args>)` или `Poison(String)`.
- Возможности: `PerTask`, приём постановки.
- Управление сценарием:

| Метод | Сбой |
|-------|------|
| `push` (через `Source`) | Обычная задача |
| `inject_poison(text)` | Отравленное сообщение в очередь |
| `fail_next_polls(n)` | Следующие n опросов возвращают `InjectedError` |
| `fail_next_acks(n)` | Следующие n ack возвращают `InjectedError`, задача возвращается в начало очереди — повторная доставка после «обрыва между исполнением и ack» |
| `close()` | После выдачи всего — «закрыт» |

- Счётчики `polls()`, `acks()`, `redeliveries()` — сценарии проверяют по ним поведение.
- Пробуждение — через `WakeHandle`, как у in-memory.
- `FaultyCodec<Args>`: `Scripted::Task` декодируется как есть, `Scripted::Poison` → `CodecError::Decode`.

**Обоснование**: критерий заявки №1. Сбои задаются явным сценарием, а не вероятностью, поэтому воспроизводятся всегда одинаково. Повторная доставка после неудачного ack моделирует at-least-once (спецификация 4.3 п. 1).

**Альтернативы**:
- Обёртка над `InMemorySource` — отклонено: in-memory хранит `Task<Args>`, а отравленное сообщение задачей не является.
- Случайные сбои с вероятностью — отклонено: недетерминированно.

### `DeliveryLedger`

**Решение**:
- `pushed(&TaskId)` и `executed(&TaskId)` — потокобезопасный учёт.
- `report() -> LedgerReport { duplicates: Vec<(TaskId, u32)>, lost: Vec<TaskId> }`:
  - `duplicates` — задачи, исполненные больше одного раза, с числом исполнений;
  - `lost` — поставленные и ни разу не исполненные.
- Списки отсортированы, поэтому отчёт сравним в тестах.
- `executions(&TaskId)` — число исполнений одной задачи.

**Обоснование**: критерий заявки №2.

### Сценарии проверяют воркер через `Runner`

**Решение**: воркер в сценарии — это то, что реализует трейт `Runner`:

```rust
pub trait Runner: Send + Sync + 'static {
    fn run(&self, setup: RunnerSetup) -> BoxFuture<'static, ()>;
}
```

`RunnerSetup` содержит:

| Поле | Значение |
|------|----------|
| `source` | `Arc<FaultySource<u32>>` |
| `codec` | `FaultyCodec<u32>` |
| `handler` | `ScenarioHandler` — клонируемая функция `TaskRequest<u32> → BoxFuture<Outcome>` |
| `max_attempts` | число попыток |
| `retry_pause` | пауза повтора |
| `stop` | `CancellationToken` |
| `registry`, `shared` | реестр метаданных и общие данные |

Контракт воркера в сценарии — минимальный:
- опрашивать до «закрыт» или `stop`;
- при «пусто» ждать пробуждения или опрашивать снова;
- декодировать;
- исполнять обработчик;
- повторять «повторить» после паузы до `max_attempts`;
- делать ack после исхода.

Сценарии (`taskcraft::testing::scenarios`), каждый под виртуальным временем вызывающего теста (`start_paused = true`):

| Сценарий | Проверяет | Дефект apalis |
|----------|-----------|---------------|
| `empty_never_ends_worker` | После 100 ответов «пусто» воркер жив и исполняет задачу, поставленную позже | A-1 |
| `boxed_abort_is_not_retried` | Обработчик возвращает `TaskError::abort` упакованной ошибки при трёх попытках — ровно одно исполнение | B-1 |
| `poison_does_not_stop_worker` | После отравленного сообщения воркер исполняет следующую задачу | B-4 |
| `cancel_during_retry_pause_stops_work` | Обработчик всегда «повторить», пауза 5 мин; `stop` во время паузы — воркер завершается меньше чем за 1 с виртуального времени, исполнение одно | A-4 (паттерн первого потребителя) |
| `wake_reaches_every_subscriber` | Для любого источника: два подписчика, одна постановка — оба получают пробуждение | A-5 |

- Сценарий возвращает `Err(ScenarioFailure)` с описанием: что ожидалось и что произошло.
- Таймауты сценариев — виртуальные (`tokio::time::timeout`), поэтому зависший воркер даёт отказ, а не повисший тест.

**Обоснование**: критерии заявки №3 и №4. Узкий `Runner` позволяет прогнать те же сценарии на настоящем воркере без переделки: его заявка добавит реализацию `Runner` поверх воркера.

**Альтернативы**:
- Писать сценарии позже, вместе с воркером — отклонено: порядок работ D-4 требует харнесс до воркера.
- Обобщить сценарии по типу аргументов — отклонено: сценариям достаточно `u32`, а обобщение усложнит `RunnerSetup`.

### Заглушки с дефектами и эталонный воркер — в тестах

**Решение**: в `crates/taskcraft/tests/harness.rs`:
- `ReferenceRunner` — минимальный правильный цикл по контракту `Runner`;
- `DefectiveRunner { empty_ends, ignore_abort, poison_stops, sleep_ignores_stop }` — тот же цикл с включаемым дефектом;
- `SingleWakerSource` — источник, у которого пробуждение получает только последний подписчик.

Каждый сценарий проверяется дважды: на эталоне — `Ok`, на заглушке со своим дефектом — `Err`.

**Обоснование**: критерий заявки №3 — «каждый сценарий падает на заглушке с таким дефектом». Проход на эталоне доказывает, что сценарий не падает всегда.

### Токен отмены — `tokio-util`

**Решение**: `tokio_util::sync::CancellationToken` для `stop` в `RunnerSetup`. `tokio-util` входит в ядро: спецификация 2.6 называет его обязательной зависимостью — сигнал остановки и признак отмены.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| Сценарий запущен без виртуального времени | Тест ждёт реальные минуты | Документация каждого сценария требует `start_paused = true`; паузы в сценариях — минуты, ошибку заметно сразу |
| Эталонный воркер в тестах расходится с настоящим | Сценарии проверяют не то | Настоящий воркер прогоняет те же сценарии через свой `Runner` в своей заявке |
| `test-util` в CI | Тесты харнесса без `--all-features` не запускаются | CI уже запускает `cargo test --all-features` |

## Архитектура

### Компонентная диаграмма

```
тест (start_paused) ──► scenarios::X(&runner) ──► Runner::run(RunnerSetup)
                              │                         │ опрос / ack
                              ▼                         ▼
                        DeliveryLedger ◄── handler  FaultySource ◄── сбои по сценарию
                              │                    (Scripted: Task | Poison)
                              ▼
                     Ok(()) | Err(ScenarioFailure)
```

## Детали реализации

### Алгоритмы

```
empty_never_ends_worker(runner):
  source = FaultySource::new(); запуск runner
  продвинуть время до тех пор, пока source.polls() < 100 (не более 10 мин виртуальных)
  если runner уже завершился → отказ «воркер завершился на пустом источнике»
  поставить задачу; ждать её исполнения (таймаут 1 мин)
  нет → отказ; stop; дождаться runner

cancel_during_retry_pause_stops_work(runner):
  handler всегда Retry; max_attempts 3; retry_pause 5 мин
  поставить задачу; ждать первого исполнения
  t0 = now; stop.cancel(); ждать runner с таймаутом 1 с
  таймаут → отказ «остановка ждала конца паузы»; исполнений > 1 → отказ
```

### Обработка edge cases

| Ситуация | Поведение |
|----------|----------|
| Неудачный ack | Задача возвращается в начало очереди, `redeliveries` +1 |
| `fail_next_polls(n)` при закрытом источнике | Сначала n ошибок, затем «закрыт» |
| Воркер не завершился после `stop` | Сценарий даёт отказ по таймауту, а не виснет |

## Тестирование

### Unit-тесты

| Что тестируем | Сценарий |
|---------------|----------|
| `FaultySource` | Каждый сбой: отравленное сообщение декодируется в ошибку; `fail_next_polls(2)` — ровно две ошибки, затем задача; `fail_next_acks(1)` — ошибка ack и повторная доставка той же задачи (критерий №1) |
| `DeliveryLedger` | Дважды исполненная и неисполненная задачи попадают в отчёт; отчёт отсортирован (№2) |

### Integration-тесты

| Что тестируем | Сценарий |
|---------------|----------|
| Сценарии на эталоне | Все пять — `Ok` |
| Сценарии на заглушках | Каждый — `Err` на заглушке со своим дефектом (№3) |
| Отмена во время паузы | Проходит на виртуальном времени: реальное время теста меньше секунды (№4) |
