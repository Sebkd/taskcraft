## Context

`crates/taskcraft-postgres/src/store.rs`.

- **Схема.** `create_schema` выполняет `SCHEMA` (`CREATE … IF NOT EXISTS`) под транзакционной advisory-блокировкой `SCHEMA_LOCK`. Таблицы `taskcraft_tasks` и `taskcraft_processes`. Индексы:
  - первичный ключ `(queue, id)`;
  - `taskcraft_tasks_ready (queue, state, next_delivery, created_at)`;
  - `taskcraft_tasks_owner (owner) WHERE owner IS NOT NULL`.
- **Обслуживание.** `upkeep` раз в тик (меньшее из `alive_interval` = 10 с и пульса аренды) отмечает процесс, продлевает аренды и удаляет **все** терминальные задачи старше срока хранения одним `DELETE`. Индекса по `updated_at` нет, поэтому каждый процесс каждые 10 с проходит всю таблицу.
- **Захват** (`PgSource::poll`): `WHERE queue AND ((state IN ('queued','deferred') AND (next_delivery IS NULL OR next_delivery <= now())) OR ($2 AND state IN (…) AND lease_until < now())) ORDER BY COALESCE(next_delivery, created_at), created_at LIMIT 1 FOR UPDATE SKIP LOCKED`.
  - `OR` двух разных условий не даёт использовать один индекс.
  - Сортировку по выражению `COALESCE` нельзя взять из индекса `ready`: на каждый опрос сортируются все готовые задачи очереди.

## Decisions

### D-1. Версия схемы и миграции

- **Таблица версии:** `taskcraft_schema (version integer NOT NULL)`, одна строка.
- **Миграции:** список `MIGRATIONS: &[&str]`, элемент `i` переводит схему в версию `i + 1`. Поддерживаемая версия — длина списка (2).
- **Как применяются.** В одной транзакции под той же `pg_advisory_xact_lock(SCHEMA_LOCK)`:
  1. создать `taskcraft_schema`, если её нет;
  2. прочитать версию; строки нет → 0;
  3. применить недостающие миграции по порядку;
  4. записать версию;
  5. зафиксировать транзакцию.

  Второй процесс ждёт на блокировке и видит готовую версию (критерий №2).
- **Версия 1** — нынешний `SCHEMA` (`IF NOT EXISTS`). База 0.1–0.2 без `taskcraft_schema` получает версию 1 без изменений, и данные сохраняются (критерий №1).
- **Версия 2** — индексы D-3, **без** `IF NOT EXISTS`: повторное применение упало бы. Значит, успех двух одновременных стартов подтверждает, что миграция прошла один раз.
- **База новее библиотеки** — `PgStoreError::SchemaTooNew { found, supported }`: «task store schema is newer than this library: found=3, supported=2». Старт отклоняется (критерий №3).

### D-2. Захват без `OR`: два оператора

- `FOR UPDATE` в `UNION` PostgreSQL не допускает. Поэтому захват — два отдельных оператора `UPDATE … FROM (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)`. Каждый идёт по своему частичному индексу.
- **Порядок: сначала задачи с истёкшей арендой, затем готовые.** В заявке сказано наоборот — «сначала готовые, затем с истёкшей арендой». Но при постоянном потоке готовых задач задачи упавшего процесса тогда ждали бы, пока очередь не опустеет. Это голодание, а это старая работа. Первый запрос по частичному индексу аренды дешёвый: обычно он пуст и стоит одного обращения к индексу.
- **Без аренды** первого оператора нет.
- **Готовые задачи:**
  - `WHERE queue = $1 AND state IN ('queued','deferred') AND COALESCE(next_delivery, created_at) <= now() ORDER BY COALESCE(next_delivery, created_at), created_at`;
  - это то же условие, что «`next_delivery` пуст или наступил»: `created_at` всегда в прошлом;
  - порядок выдачи прежний (правило 2.3.25 п. 2).
- **Истёкшие аренды:** `WHERE queue = $1 AND state IN ('accepted','running','retry_waiting') AND lease_until < now() ORDER BY lease_until`.
- **Вне захвата** — уведомление «задача подхвачена» и признак «чья была» — без изменений.

### D-3. Индексы (миграция 2)

| Индекс | Определение | Для чего |
|--------|-------------|----------|
| `taskcraft_tasks_due` | `(queue, (COALESCE(next_delivery, created_at)), created_at) WHERE state IN ('queued','deferred')` | Захват готовых: поиск и порядок из индекса |
| `taskcraft_tasks_lease` | `(queue, lease_until) WHERE state IN ('accepted','running','retry_waiting')` | Захват по истёкшей аренде |
| `taskcraft_tasks_finished` | `(updated_at) WHERE state IN ('succeeded','failed','panicked','cancelled')` | Очистка по сроку хранения |

- **Старый `taskcraft_tasks_ready` удаляется:** его заменяет `due`.
- **Без изменений** остаются `owner` (возврат задач при рестарте) и первичный ключ (статус, отмена, повторный запуск, постановка).

### D-4. Очистка: раз в минуту, порциями

- **Настройки построителя:**
  - `PgStoreBuilder::cleanup_interval(Duration)`, по умолчанию 60 с;
  - `cleanup_batch(u32)`, по умолчанию 1000.

  Ноль — ошибка конфигурации «duration must be positive» или «cleanup batch must be at least 1».
- **Когда:** в цикле `upkeep`, если с прошлой очистки прошло не меньше интервала. Первая очистка — на первом тике.
- **Одна порция:** `DELETE FROM taskcraft_tasks WHERE (queue, id) IN (SELECT queue, id … WHERE state IN (терминальные) AND updated_at < now() − срок ORDER BY updated_at LIMIT batch)`.
- **Порции повторяются**, пока удаляется полная порция. Каждая — короткая транзакция; накопленный хвост уходит за один запуск, не держа долгих блокировок.

### D-5. Проверки на изолированных схемах PostgreSQL

- **Изоляция.** Тесты миграций и `EXPLAIN` создают свою схему PostgreSQL (`taskcraft_test_<uuid>`). Пул открывается с `SET search_path` на неё, после теста — `DROP SCHEMA … CASCADE`. Общая таблица остальных тестов не трогается, а миллион строк не остаётся в базе.
- **Критерии №1 и №2:** в изолированной схеме создаётся схема версии 0.1 (её SQL — копия в тесте) с задачами и историей. Затем два `PgStore` стартуют одновременно (`tokio::join!`):
  - оба успешны;
  - версия 2;
  - индексы на месте;
  - задачи и история сохранены.
- **Критерий №3:** версия 99 → `SchemaTooNew`.
- **Критерий №4** — модульный тест в пакете: тексты запросов закрыты внутри пакета, их проверяет только модульный тест.
  - 1 млн строк через `generate_series`: 90% терминальных, остальные готовые, отложенные и захваченные;
  - затем `ANALYZE` и `EXPLAIN (FORMAT JSON)` трёх запросов: захват готовых, захват по аренде, порция очистки;
  - в планах нет `Seq Scan` по `taskcraft_tasks`, используются индексы `due`, `lease`, `finished`.
- **Запуск:** тесты идут в CI в задании PostgreSQL. Без `TASKCRAFT_POSTGRES_URL` они пропускаются, как и прочие тесты хранилища.

### D-6. Тексты запросов

Запросы захвата и очистки выносятся в константы `sql.rs` пакета. Их используют и код, и тест `EXPLAIN`, поэтому проверяются те же тексты, что выполняются.

## Risks / Trade-offs

| Риск | Последствия | Mitigation |
|------|------------|------------|
| `CREATE INDEX` в транзакции миграции блокирует запись в таблицу на время построения | На большой базе старт первого процесса новой версии задерживает работу остальных на время построения индексов | Сейчас баз с большой историей нет (пилот впереди); в README пакета — что миграция строит индексы при первом старте. `CONCURRENTLY` вне транзакции — если понадобится, отдельной заявкой |
| Процесс старой версии на базе версии 2 | Без проверки версии он не знает о ней; его запрос захвата медленнее, но корректен | README пакета: обновлять все процессы; новые версии будут отказываться стартовать на более новой схеме |
